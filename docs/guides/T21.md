# [T21] Rubik Pi에 서버 올리기와 실측 — 지침서

2026-11-13 · 이광호

## 목표

T30에서 초기 설정을 마친 Rubik Pi 3에 앱 서버를 올리고, mock STT로 돌려 자원 사용량을 잽니다. 끝나면 아래가 모두 됩니다.

1. 보드에 Node 22.22.0(nvm), PostgreSQL 16(apt), 이 저장소의 `main`이 있고, `npm ci`·`npm run build:web`·`npm run db:migrate`가 통과합니다.
2. 서버를 켜면 Mac 브라우저의 `http://rubikpi.local:3000`에서 웹앱이 열리고, mock 녹음 → 실시간 자막 → 히스토리 상세 → txt·md 내려받기가 됩니다.
3. 10분 mock 녹음 동안 서버와 PostgreSQL의 메모리·CPU를 1분마다 잰 값, `free -h`, `df -h`가 기록되어 있습니다(T30 기준값과 비교).
4. 앞선 작업에서 T21로 넘긴 확인 항목의 결과가 기록되어 있습니다(아래 '넘어온 확인').

## 배경과 전제, 범위

- 보드 상태(T30, 2026-11-13): Ubuntu 24.04.2, `aarch64`, 커널 `6.8.0-1051-qcom`, 메모리 7.1 GiB(사용 약 550 MiB), 디스크 105 GB 남음, CPU 8개, 클럭 정책 `schedutil`. `ssh rubikpi`로 키 로그인, `ubuntu` 계정은 `sudo`에 비밀번호가 필요 없음. 팀 서비스(`audiostack`, `whisper-engine`)와 `~/rubikpi`는 없음. Node·PostgreSQL 없음, `git`·`curl`·`xz`는 있음.
- 네트워크는 사용자 휴대폰 핫스팟입니다. Mac은 이 핫스팟에서 IPv4 주소를 받지 않아 보드에 IPv6로만 닿습니다(T30). 서버는 `app.listen(env.port)`로 열어 IPv4·IPv6를 함께 받으므로 고칠 것이 없습니다.
- 서버에 로그인이 없으므로 믿을 수 있는 네트워크(내 핫스팟)에서만 켭니다. PostgreSQL은 Ubuntu 기본값대로 보드 안(`localhost`)에서만 받습니다.
- STT는 mock입니다(`STT_MODE` 비움). mock은 단어 하나를 200 ms마다 내보내, 문장(final)이 1초에 하나쯤 나옵니다. 실제 말보다 빽빽하므로 이 값은 넉넉한 쪽의 추정입니다.
- 마이크·데몬·엔진이 없어 하드웨어 파트(D5)와 합의할 것이 없습니다. 데몬 경로(HW-1)는 T26 전에 정합니다.
- CPU 클럭 정책은 바꾸지 않고 기본 `schedutil`에서 잽니다. AI 파트의 엔진 측정값은 `performance` 기준이므로, 비교할 때 정책을 함께 적습니다(`team-questions.md` 3장).

- 하는 것: 코드 올리기(git bundle), Node·PostgreSQL 설치, DB 계정과 보드용 `.env`, 의존성 설치·웹 빌드·마이그레이션, 서버 실행, 브라우저 확인, 10분 실측, 넘어온 확인 항목, 기록.
- 하지 않는 것: 저장소 코드 변경(찾은 문제는 기록만, 사용자 결정), PostgreSQL 설정 변경(D8, 실측 뒤 정함), 서버 자동 시작(systemd, T26·T27), `apt full-upgrade`(AI-2 확인 뒤), 클럭 정책 변경, QNN·엔진·모델·`audio-stack`(T26), 마이크(T27), 방화벽, `git push`.

## 진행 순서

모든 명령은 Claude가 Mac에서 실행합니다. 보드 명령은 `ssh rubikpi '…'`로 보냅니다. 비대화형 SSH에서는 `~/.bashrc`가 nvm을 읽지 않으므로 Node 명령 앞에 `source ~/.nvm/nvm.sh`를 붙입니다.

### 1단계. 코드 올리기 (git bundle)

```bash
# Mac
git bundle create "$TMPDIR/web-app-main.bundle" main
git bundle verify "$TMPDIR/web-app-main.bundle"
scp "$TMPDIR/web-app-main.bundle" rubikpi:
ssh rubikpi 'git clone -b main ~/web-app-main.bundle ~/web-app && git -C ~/web-app log -1 --format=%h'
git rev-parse --short main
```

- 확인: 보드와 Mac의 커밋 번호가 같습니다. `ssh rubikpi 'ls -a ~/web-app'`에 `.env`, `CLAUDE.md`, `node_modules`가 없습니다.
- 나중에 고칠 때: Mac에서 bundle을 다시 만들어 같은 이름으로 보내고, 보드에서 `git -C ~/web-app pull`.

### 2단계. Node 22.22.0 (nvm)

```bash
ssh rubikpi 'curl -fsSLo /tmp/nvm-install.sh https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.8/install.sh && head -5 /tmp/nvm-install.sh'
ssh rubikpi 'bash /tmp/nvm-install.sh'
ssh rubikpi 'source ~/.nvm/nvm.sh && cd ~/web-app && nvm install && nvm alias default 22.22.0 && node -v && npm -v'
```

- 확인: `node -v`가 `v22.22.0`. 시간대 데이터(T11): `node -p "process.versions.icu + ' ' + Intl.DateTimeFormat().resolvedOptions().timeZone + ' ' + new Date().toLocaleString('ko-KR', { timeZone: 'Asia/Seoul' })"`가 ICU 판, `Asia/Seoul`, 보드 `date`와 같은 시각을 출력합니다.

### 3단계. PostgreSQL 16과 DB 계정

```bash
ssh rubikpi 'sudo apt-get install -y postgresql-16'
ssh rubikpi 'systemctl is-active postgresql; sudo -u postgres psql -Atc "show server_version; show listen_addresses; show shared_buffers; show max_connections"'
```

DB 계정과 보드용 `.env`(비밀번호는 보드에서 만들고 출력하지 않음):

```bash
ssh rubikpi 'set -e; umask 077; pw=$(openssl rand -hex 16)
sudo -u postgres psql -v ON_ERROR_STOP=1 -qc "create role transcriber login password '"'"'$pw'"'"'"
sudo -u postgres createdb -O transcriber transcriber
printf "PORT=3000\nDB_URL=postgres://transcriber:%s@localhost:5432/transcriber\nSTT_URL=http://localhost:9000\nSTT_MODE=\n" "$pw" > ~/web-app/.env
stat -c "%a %n" ~/web-app/.env'
```

- 확인: `systemctl is-active postgresql`이 `active`, 판이 16.x, `listen_addresses`가 `localhost`. `.env` 권한이 `600`.

### 4단계. 의존성, 웹 빌드, 마이그레이션

```bash
ssh rubikpi 'source ~/.nvm/nvm.sh && cd ~/web-app && npm ci && npm run build:web && npm run db:migrate'
ssh rubikpi 'du -sh ~/web-app/node_modules ~/web-app/apps/web/dist ~/.nvm'
```

- 확인: 세 명령이 오류 없이 끝나고, 마이그레이션이 `001`~`003`을 적용합니다. 보드에서 `npm run typecheck`와 `npm test`도 통과합니다(같은 코드가 arm64 Linux에서 도는지 확인).
- `npm ci`가 받은 양은 출력의 `added … packages`와 시간으로 적습니다.

### 5단계. 서버 켜기와 쉬는 상태

```bash
ssh rubikpi 'mkdir -p ~/t21 && cd ~/web-app && source ~/.nvm/nvm.sh && (setsid nohup npm run dev:server > ~/t21/server.log 2>&1 < /dev/null &)'
ssh rubikpi 'sleep 5; cat ~/t21/server.log; ss -ltnpH "sport = :3000"'
curl -s http://rubikpi.local:3000/health; echo
curl -sI http://rubikpi.local:3000/ | head -1
```

- 확인: 기록에 `ready`, `STT_MODE=mock`, `web - 웹앱 빌드를 내보냅니다`. `ss`가 `*:3000`(모든 주소, T04). Mac에서 `/health`가 DB 정상, `/`가 `200`.
- 프로세스 묶음(`npm`, `tsx`, 서버 `node`)의 RSS를 한 번 적습니다: `ssh rubikpi 'ps -u ubuntu -o pid,ppid,rss,args | grep -E "npm|tsx|node" | grep -v grep'`.

측정 스크립트를 보드에 둡니다(`~/t21/sample.sh`, 저장소 밖).

```bash
#!/usr/bin/env bash
# T21 실측: 1분마다 서버와 PostgreSQL의 메모리(PSS)·누적 CPU 시간, 시스템 메모리를 적는다. sudo로 실행
# 사용: sudo bash ~/t21/sample.sh <횟수> <출력 파일>
n=${1:-11}; out=${2:-/home/ubuntu/t21/samples.txt}
srv=$(ss -ltnpH 'sport = :3000' | grep -o 'pid=[0-9]*' | head -1 | cut -d= -f2)
tick=$(getconf CLK_TCK)
echo "time srv_pss_kb srv_cpu_s pg_pss_kb pg_cpu_s pg_procs mem_used_mb mem_avail_mb" | tee "$out"
for i in $(seq 1 "$n"); do
  # 서버가 없으면 /proc//stat(= /proc/stat)을 읽지 않도록 건너뛴다
  sp=; sc=
  [ -n "$srv" ] && sp=$(awk '/^Pss:/ {print $2}' /proc/$srv/smaps_rollup 2>/dev/null)
  [ -n "$srv" ] && sc=$(awk -v t="$tick" '{printf "%.2f", ($14+$15)/t}' /proc/$srv/stat 2>/dev/null)
  pg=$(pgrep -u postgres)
  pp=$(for p in $pg; do awk '/^Pss:/ {print $2}' /proc/$p/smaps_rollup 2>/dev/null; done | awk '{s+=$1} END {print s+0}')
  pc=$(for p in $pg; do awk '{print $14+$15}' /proc/$p/stat 2>/dev/null; done | awk -v t="$tick" '{s+=$1} END {printf "%.2f", s/t}')
  pn=$(echo $pg | wc -w)
  m=$(free -m | awk '/^Mem:/ {print $3, $7}')
  # 서버가 없으면 서버 두 칸은 '-'
  echo "$(date +%T) ${sp:--} ${sc:--} $pp $pc $pn $m" | tee -a "$out"
  [ "$i" -lt "$n" ] && sleep 60
done
```

- 1분 사이 CPU 사용률은 `(다음 CPU 시간 − 이번 CPU 시간) / 60 × 100`(%)로 계산합니다. 코어 하나를 다 쓰면 100%입니다.
- PostgreSQL 합계는 그 순간 살아 있는 프로세스만 셉니다. 연결이 끊긴 프로세스의 CPU 시간은 빠집니다.

### 6단계. 브라우저 확인과 10분 실측

1. Mac 브라우저로 `http://rubikpi.local:3000`을 엽니다. 위쪽 서버 상태가 정상입니다.
2. 측정을 시작합니다: `ssh rubikpi 'sudo bash ~/t21/sample.sh 11 ~/t21/samples-10min.txt'`(백그라운드). 첫 줄은 녹음 전 값입니다.
3. 바로 녹음 화면에서 **녹음 시작**을 누릅니다. 자막이 흐르는지 봅니다. 세션 번호를 적습니다.
4. 8분째에 Mac에서 SSE 연결 10개를 2분 동안 엽니다(동시 접속, T07). 같은 때 다시 연결 한 번의 크기와 시간을 잽니다(T09·T15).

   ```bash
   A=$(dscacheutil -q host -a name rubikpi.local | awk '/ipv6_address/ {print $2; exit}'); R="rubikpi.local:3000:[$A]"
   for i in $(seq 10); do (curl -sN --resolve "$R" --max-time 120 http://rubikpi.local:3000/api/sessions/<번호>/events > /dev/null &); done
   curl -sN --resolve "$R" --max-time 3 -o "$TMPDIR/t21-replay.txt" -w '%{size_download} bytes, 첫 바이트 %{time_starttransfer}s\n' http://rubikpi.local:3000/api/sessions/<번호>/events
   grep -c '^id:' "$TMPDIR/t21-replay.txt"
   ```

5. 10분째 마지막 측정 줄이 나오면 **녹음 종료**를 누릅니다. 히스토리 상세로 넘어가고, txt·md를 내려받습니다.

- 확인: 화면 자막이 끊기지 않습니다. 상세의 문장 수 = 보드 `psql`의 행 수 = txt의 문장 줄 수. `segment_id`가 0부터 빈 번호 없이 이어집니다.

  ```bash
  ssh rubikpi 'sudo -u postgres psql -d transcriber -Atc "select count(*), min(segment_id), max(segment_id) from segments where session_id = <번호>"'
  ```

### 7단계. 히스토리 응답 시간과 시간대

핫스팟에서는 Mac이 `rubikpi.local`을 해석할 때 IPv4 응답을 5초 기다립니다(결과 참고). 응답 시간에 이 5초가 섞이지 않도록 주소를 고정합니다. 주소는 문서에 적지 않습니다.

```bash
A=$(dscacheutil -q host -a name rubikpi.local | awk '/ipv6_address/ {print $2; exit}')
for u in /api/sessions /api/sessions/<번호> "/api/sessions/<번호>/export?format=txt" "/api/sessions/<번호>/export?format=md"; do
  curl -s --resolve "rubikpi.local:3000:[$A]" -o /dev/null -w "%{http_code} %{time_total}s $u\n" "http://rubikpi.local:3000$u"
done
ssh rubikpi 'date "+%F %T %Z"'
```

- 확인: 모두 `200`. 응답 시간을 적습니다(쿼리 시간 제한 판단 근거, T10·T13). txt 머리말의 시작 시각이 녹음을 시작한 한국 시각과 같습니다(T11).

### 8단계. DB가 멈췄을 때 (세그먼트 대기열, T08)

1. 새 녹음을 시작합니다(브라우저). 측정을 시작합니다: `sudo bash ~/t21/sample.sh 5 ~/t21/samples-dbstop.txt`.
2. 1분 뒤 `ssh rubikpi 'sudo systemctl stop postgresql'`. 2분 동안 그대로 둡니다.
3. `ssh rubikpi 'sudo systemctl start postgresql'`. 1분 더 둔 뒤, 측정이 끝나면 녹음을 종료합니다.

- 확인: 멈춘 동안 서버가 죽지 않고 자막이 계속 흐릅니다. 다시 켠 뒤 `count(*)`가 `max(segment_id) + 1`과 같습니다(쌓아 둔 final이 모두 저장됨). 멈춘 2분 동안 서버 PSS가 얼마나 늘었는지 적습니다.

### 9단계. 서버가 꺼졌을 때 배너 (T15)

1. 새 녹음을 시작하고 30초 둡니다.
2. 서버를 끕니다: `ssh rubikpi 'pkill -TERM -f "[s]rc/index.ts"'`.
3. 확인: 화면 위쪽에 끊김 배너가 나오고, 서버 상태가 '서버가 답하지 않습니다' 쪽으로 바뀝니다(노트북에서는 Vite 프록시가 `502`를 줬지만, 보드에서는 연결 거부).
4. 5단계 첫 명령으로 서버를 다시 켭니다.
5. 확인: 배너가 사라지고 서버 상태가 정상으로 돌아옵니다. 그 세션은 히스토리에서 끝난 세션(종료 또는 중단됨)으로 보이고, 끈 때까지의 문장이 있습니다.

### 1. SIGTERM으로 서버가 꺼지지 않음

서로가 서로를 기다리는 구조입니다.

1. `apps/server/src/index.ts`의 `shutdown()`이 `server.close()`를 먼저 부릅니다. Node 22의 `close()`는 그 순간 쉬고 있는 연결만 닫고 새 연결만 거부합니다. 이미 열린 연결로 오는 요청은 계속 처리합니다.
2. 그다음 `disconnectSubscribers()`가 SSE 응답을 끝냅니다. SSE가 쓰던 소켓은 닫히지 않고 keep-alive로 남습니다(Node 기본 5초, 서버에서 바꾸지 않음).
3. 웹앱은 1초 뒤에 다시 시도합니다(`apps/web/src/api/useSessionStream.ts`의 `retryDelayMs`). 같은 소켓으로 `/api/sessions/active`를 묻습니다. 세션 정리(`sessions.shutdown()`)는 `close` 콜백 안에서만 돌아, 세션은 아직 `recording`입니다. 그래서 웹앱이 SSE를 다시 엽니다. `apps/server/src/sessions/manager.ts`의 `subscribe`에는 종료 중인지 보는 확인이 없어 이 구독을 받습니다.
4. `close` 콜백은 모든 연결이 닫혀야 불리고, 이 SSE 연결은 세션이 끝나야 닫히고, 세션은 `close` 콜백에서 끝납니다. 브라우저가 녹음 화면을 떠나야 풀립니다.

- 재현: Node 22.22.0의 `http` 서버와 keep-alive 클라이언트로 같은 순서를 돌렸습니다(SSE 연결 → `close()` → SSE 끝냄 → 1초 뒤 활성 세션 확인과 SSE). `close()` 뒤에도 같은 소켓으로 요청 2개가 처리됐고, `close` 콜백은 불리지 않았습니다.
- 끊김 배너가 나오지 않은 이유: SSE 재연결이 1초 만에 성공했습니다. `/health`는 새 연결이 필요해 거부되어, 위쪽 상태만 '서버에 연결하지 못했습니다'였습니다.
- 노트북(T18)에서 생기지 않은 것은 기록상 Vite 프록시를 거쳐서입니다. 이번에 다시 확인하지는 않았습니다.
- 영향: systemd로 끄거나 다시 켤 때(T26·T27) 기본 90초 동안 멈췄다가 강제 종료됩니다. 그동안 녹음은 계속됩니다.
- 고칠 방향(고르지 않음): (가) 종료할 때 세션을 먼저 중단하고 `server.close()`를 부름. 웹앱의 재시도가 '진행 중인 세션 없음'을 받아 상세 화면으로 넘어감. (나) 종료 중에는 `subscribe`와 활성 세션 확인이 `503`. (다) 몇 초 뒤에도 안 끝나면 `server.closeAllConnections()`. 추천은 (가)와 (다)를 함께 하는 것입니다. `index.ts` 안에서 끝나는 작은 변경입니다.

### 2. 핫스팟에서 이름 해석 5초

- 핫스팟에서 Mac은 IPv4 주소를 받지 못해 mDNS를 IPv6로만 묻습니다.
- 보드의 avahi는 `publish-a-on-ipv6`가 기본값 `no`입니다(`/etc/avahi/avahi-daemon.conf`에서 주석으로 남은 기본값). IPv6로 오는 mDNS 질의에는 IPv4 주소(A 레코드)를 답하지 않습니다.
- Mac은 오지 않는 A 응답을 약 5초 기다린 뒤 IPv6 주소로 접속합니다. curl은 매번 다시 해석해 매번 5초, 브라우저는 결과를 저장해 첫 접속만 느립니다.
- Mac이 그 핫스팟에서 IPv4를 받지 못한 이유는 확인하지 않았습니다.

### 3. 공유기 DNS가 `.local`에 외부 주소를 답함

- 이 공유기의 DNS는 `local.` 영역을 자기 것이라고 답하고(SOA), 모든 `.local` 이름에 같은 외부 주소를 줍니다. 이때 macOS는 `.local` 이름을 mDNS와 일반 DNS 양쪽에 묻습니다.
- `dns-sd -G v4 rubikpi.local`에서 일반 DNS의 외부 주소(인터페이스 0, TTL 약 75분)가 1 ms 만에, mDNS의 사설 주소(TTL 120초)가 433 ms 뒤에 왔습니다. Mac의 시스템 해석은 먼저 온 답을 씁니다.
- 이것으로 30초마다 105번 중 98번이 외부 주소만 나온 것과, 사설 주소가 나온 7번이 모두 `dns-sd` 직후(mDNS 답이 캐시에 있을 때)였던 것이 설명됩니다.
- 보드를 붙인 직후 몇 분 동안 빨랐던 이유는 확인하지 못했습니다. 보드가 막 붙으며 스스로를 알린 정보가 캐시에 있었던 것으로 추정합니다.
- 이 네트워크에서 이름으로 접속하면 요청이 모르는 외부 서버로 갈 수 있습니다. 접속 방법을 정할 때까지 IP로 접속합니다.

### 4. 보드 무응답 (기존 기록 정정)

부팅 기록(`journalctl --list-boots`, `last -x`)으로 본 순서입니다.

| 부팅 | 시각 | 내용 |
| --- | --- | --- |
| -2 | 11-13 14:58:31~15:53:34 | T21을 한 부팅. 15:53:16에 Mac에서 SSH 접속, 15:53:34에 `systemd-poweroff`로 정상 전원 끄기. 일지에는 없는 일입니다 |
| -1 | 알 수 없음 | 리눅스까지 정상으로 올라옴(28.5초에 부팅 완료, cloud-init까지). 끄는 기록 없이 끝남 |
| 0 | 11-14 아침 | 사용자가 전원을 다시 꽂은 뒤. 1시간 녹음을 한 부팅 |

- 부팅 -1의 시각을 알 수 없는 이유: 보드에는 배터리로 도는 시계(RTC)가 없습니다. 이때 와이파이에도 붙지 못해(`lo`만 활성, snapd의 DNS 조회 실패) `systemd-timesyncd`가 시계를 마지막으로 저장한 시각(15:53:34)으로 되돌렸습니다. 기록의 15:53~15:55는 실제 시각이 아닙니다.
- 부팅 -1은 5분 넘게 살아 있었습니다. `timesyncd`는 60초마다 시각을 저장하는데, 오늘 부팅이 15:58:36으로 시계를 되돌렸습니다. 저널이 15:55:01에서 끝난 것은 저널이 5분마다 디스크에 쓰기 때문입니다(`SyncIntervalSec` 기본 5분). 마지막 몇 분은 사라졌습니다.
- 끄는 기록이 없으므로 부팅 -1은 전원이 끊겼거나 멈췄습니다. 아침의 '전원 LED 켜짐, 콘솔 무응답'과 맞춰 보면 둘 중 하나입니다.
  - (가) 꽂아 둔 채로 멈췄다. LED 켜짐·콘솔 무응답과 맞습니다.
  - (나) 누가 뽑았다가 오늘 다시 꽂았는데, 첫 번째에 켜지지 않았다.
- 둘을 가르려면 집에서 꽂은 뒤 오늘 아침까지 계속 꽂혀 있었는지 알아야 합니다. (가)라면 사람 없이 운용할 때(T26·T27) 문제가 됩니다. 다시 생기면 콘솔 화면과 `journalctl -b -1`을 남깁니다.
- 함께 드러난 위험: 기기가 네트워크 없이 부팅하면 시계가 마지막 저장 시각부터 시작합니다. 그러면 녹음 시작 시각과 내보내기 머리말(T11·T13)이 틀린 값으로 저장될 수 있습니다. T26·T27에서 대책을 정합니다.

### 5. `dev:server` 프로세스 묶음

- `apps/server/package.json`에는 `dev`(`tsx --env-file=../../.env src/index.ts`)뿐이고, 빌드나 `start` 스크립트가 없습니다. 서버는 개발용 실행 방식으로만 돕니다.
- 루트 `dev:server`(`npm run dev -w @app/server`) → `npm` → `sh` → `tsx` → 서버 `node`와 `esbuild` 순서로 떠서 7개(`npm` 둘, `sh` 둘)가 됩니다.
- SIGKILL 시험에서 `npm error` 7줄이 찍힌 것도 이 `npm` 래퍼 때문입니다.

### 6. 작은 것들

- 1시간 메모리 추정(22 MB)이 빗나간 이유: 처음 10분의 증가(+3.7~4.0 MB)는 대부분 시작 직후 한 번 늘어나는 몫이었고, 이것을 6배 했습니다. 그 뒤로는 10분에 약 0.5 MB씩 늘었습니다. final 목록(T09) 때문인지는 따로 재지 않았습니다.
- PostgreSQL PSS 차이(11-13 42 MB, 11-14 30 MB): 원인은 확인하지 않았습니다. 두 날 모두 평평해 새는 것은 아닙니다.
- 11-13에 고친 명령 세 가지:
  - `pkill -f "src/index.ts"`: SSH가 띄운 셸의 명령줄에도 같은 문자열이 있어 그 셸까지 죽였습니다.
  - 측정 스크립트: 서버가 없을 때 변수가 비어 `/proc//stat`(= `/proc/stat`)을 읽었습니다.
  - `nvm install … | tail`: 파이프 앞쪽이 하위 셸에서 돌아 PATH 변경이 남지 않았습니다.
- 와이파이 암호 두 번 실패: 원인은 확인하지 못했습니다. 첫 시도에서 `Password:` 앞에 방향키 입력(`^[[B^[[B`)이 찍혀, 그 입력이 암호에 섞였을 수 있습니다(추정).

### 공통 원인

- 노트북과 기기의 차이: 노트북은 Vite 프록시를 거치고, 기기는 Express가 웹앱을 직접 내보냅니다(1). 실행 방식도 개발용 그대로입니다(5). 노트북에서 생기지 않던 문제가 기기에서 처음 드러났습니다.
- mDNS 이름에 기댄 접속: 네트워크마다 다른 방식으로 깨졌습니다(2, 3).
- 사람 없이 운용할 준비 부족: RTC가 없고, 보드가 멈췄을 때 남는 기록이 부족합니다(4).
