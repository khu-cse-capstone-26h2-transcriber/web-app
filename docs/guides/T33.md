# [T33] 서버 빌드와 운용 실행 방식 — 지침서

2026-11-14 · 이광호

## 목표

서버를 개발용 실행 방식(`tsx`)이 아니라, 미리 묶은 JavaScript 파일 하나를 `node`로 바로 띄우는 방식으로도 돌릴 수 있게 합니다. 끝나면 아래가 됩니다.

1. `npm run build:server`가 `apps/server/dist/index.js`(소스 맵 포함)를 만듭니다.
2. 저장소 루트에서 `node --enable-source-maps --env-file=.env apps/server/dist/index.js`로 서버가 뜨고, 프로세스는 `node` 하나입니다.
3. 이렇게 띄운 서버도 웹앱(`apps/web/dist`)과 API를 같은 포트에서 내보냅니다(T31과 같음).
4. SIGTERM으로 지금처럼 끝납니다(T32와 같음).
5. 개발 방식(`npm run dev:server`)은 지금과 똑같이 동작합니다.

## 배경과 전제, 범위

- T21(2026-11-13) 찾은 문제 5입니다. 원인은 `docs/guides/T21.md` '원인 분석 (2026-11-14)' 5절에 있습니다.
  - 서버 스크립트는 `dev`(`tsx --env-file=../../.env src/index.ts`)뿐입니다.
  - 루트 `npm run dev:server`는 `npm` → `sh` → `tsx` → 서버 `node`와 `esbuild` 순서로 떠서 프로세스가 7개, 약 100 MB입니다. 서버 프로세스만은 약 63~70 MB입니다.
- T26은 엔진·앱 서버·PostgreSQL을 함께 돌려 메모리·CPU를 재고, 그 값으로 D8(PostgreSQL 메모리 설정, SQLite 전환)을 정합니다. 개발 도구 몫이 섞이지 않게, T26 전에 운용 방식으로 띄울 수 있어야 합니다(2026-11-14 사용자 결정, T26 전 점검 8번).
- 지금 설정에서 `tsc`로 JS를 내보내는 방법은 맞지 않습니다.
  - 상대 import에 확장자가 없습니다(`./app`). 설정은 `moduleResolution: Bundler`, `noEmit`입니다.
  - `@app/shared`의 `main`이 TS 원본(`src/index.ts`)입니다.
  - 그래서 Node ESM으로 바로 돌리려면 import를 모두 고치고 공용 패키지도 따로 빌드해야 합니다. 묶는 도구(esbuild)는 지금 설정과 맞습니다.
- 경로 하나가 소스 파일 위치에 묶여 있습니다. `src/http/web.ts`의 `WEB_DIST_DIR`은 `import.meta.url` 기준 `../../../web/dist`입니다. 묶은 파일(`dist/index.js`)에서는 깊이가 달라 틀린 곳을 가리킵니다.

- 하는 것: esbuild 묶기 스크립트(`build`, 루트 `build:server`), 실행 스크립트(`start`, 루트 `start:server`), `WEB_DIST_DIR`을 묶은 파일에서도 맞게 고치기, esbuild를 직접 의존성으로 적기, 관련 문서(`CLAUDE.md` 명령어 목록 제안 포함).
- 하지 않는 것: 마이그레이션 묶기(`db:migrate`는 지금처럼 `tsx`로 돎. `MIGRATIONS_DIR`은 그대로), systemd 서비스(T26·T27), 보드에서 확인(T26), CPU 고정(T26), 웹 빌드 방식 변경, 단위 테스트(핵심 로직이 아님, CLAUDE.md 규칙).

## 착수 전 확인

아래는 사용자가 2026-11-14에 정했습니다(T26 전 점검 8번에서 '(다) esbuild로 묶기'를 고름).

| 항목 | 결정 | 비고 |
| --- | --- | --- |
| 작업 단위 | 새 작업 T33, T26 전에 노트북에서 | 보드 없이 끝냄 |
| 실행 방식 | esbuild로 서버를 파일 하나로 묶고 `node`로 실행 | (가) 그대로, (나) `node --import tsx`, (라) `tsc` 내보내기는 고르지 않음 |
| 브랜치 | `main`(`0e28b2e`)에서 `feat/t33-server-build` | push 안 함 |

아래는 추천 방식을 따르며 앱 파트가 정한 구현 세부입니다. 다르게 하고 싶으면 사용자가 바꿉니다.

| 항목 | 정한 것 | 이유 |
| --- | --- | --- |
| 묶는 범위 | 우리 코드와 `@app/shared`만 묶고 `express`, `pg`는 묶지 않음(`--external`) | 두 패키지는 CommonJS라 ESM 한 파일로 묶으면 `require` 처리가 따로 필요함. 보드에는 어차피 `npm ci`로 `node_modules`가 있음 |
| 출력 | `apps/server/dist/index.js`와 소스 맵, ESM, `node22` 대상 | `dist/`는 이미 `.gitignore`에 있음. 소스 맵으로 오류 줄 번호를 원본 기준으로 봄(`--enable-source-maps`) |
| `WEB_DIST_DIR` | 이 파일에서 위로 올라가며 처음 만나는 `package.json`이 있는 폴더(= `apps/server`)를 찾고, 그 옆 `../web/dist`로 함 | `src/http/web.ts`에서도 `dist/index.js`에서도 같은 폴더를 찾음. 환경변수로 받지 않는다는 T31 결정은 유지 |
| esbuild 판 | 지금 설치된 `0.28.2`를 `@app/server`의 `devDependencies`에 고정 | 지금은 `tsx`를 통해 간접으로만 깔려 있어, `tsx`가 바뀌면 사라질 수 있음 |
| `.env` 읽기 | 개발 방식과 같이 Node의 `--env-file` | 코드 변경 없음 |
| 측정·서비스용 실행 | `npm run start:server` 대신 `node`를 바로 실행 | `npm run`은 다시 `npm`·`sh` 래퍼를 띄움. `start:server`는 노트북 편의용 |

## 구현 방향

### 스크립트

`apps/server/package.json`:

```json
"build": "esbuild src/index.ts --bundle --platform=node --format=esm --target=node22 --sourcemap --outfile=dist/index.js --external:express --external:pg",
"start": "node --enable-source-maps --env-file=../../.env dist/index.js"
```

루트 `package.json`:

```json
"build:server": "npm run build -w @app/server",
"start:server": "npm run start -w @app/server"
```

측정과 서비스(보드)에서는 저장소 루트에서 아래처럼 바로 띄웁니다.

```bash
node --enable-source-maps --env-file=.env apps/server/dist/index.js
```

### `WEB_DIST_DIR`

`src/http/web.ts`에서 `import.meta.url`이 가리키는 폴더부터 위로 올라가며 `package.json`이 있는 첫 폴더를 찾습니다. 개발 방식에서는 `apps/server/src/http` → `apps/server/src` → `apps/server`, 묶은 파일에서는 `apps/server/dist` → `apps/server`에서 멈춥니다. 찾지 못하면(있을 수 없는 경우) 시작할 때 오류로 알립니다.

## 폴더 구조와 파일

| 파일 | 변경 |
| --- | --- |
| `apps/server/package.json` | `build`, `start` 스크립트, `esbuild` devDependency |
| `package.json` | `build:server`, `start:server` |
| `package-lock.json` | `esbuild` 직접 의존성 |
| `apps/server/src/http/web.ts` | `WEB_DIST_DIR`을 서버 패키지 폴더 기준으로 |
| `docs/guides/T33.md` | 이 지침서와 결과 |

새 파일은 이 지침서 하나입니다. 묶은 결과물(`apps/server/dist/`)은 커밋하지 않습니다.

## 구현 순서

1. `npm install -D esbuild@0.28.2 -w @app/server`
2. 스크립트 네 개를 넣습니다.
3. `WEB_DIST_DIR`을 고칩니다.
4. `npm run typecheck`, `npm test`
5. 아래 완료 기준을 노트북에서 확인합니다.

노트북에서 `docker compose up -d`, `npm run db:migrate`, `npm run build:web`을 한 뒤 확인합니다.

## 확인하지 않는 것

- 보드(Ubuntu, arm64)에서 묶고 실행하기: T26에서 합니다. esbuild의 arm64 바이너리는 T21에서 `tsx`가 이미 보드에서 썼습니다.
- 보드 PSS 기준 메모리 차이: T26 측정에서 봅니다.
- systemd 서비스로 띄우기: T26·T27.

지침서와 다른 점:

- `npm install -D -E esbuild@0.28.2`가 `package-lock.json`에서 다른 패키지 여러 개에 `"peer": true` 표시를 더했습니다. npm이 잠금 파일 정보를 다시 계산한 것이고, 설치되는 판은 바뀌지 않았습니다(`npm install` 결과 변경 0개).

- `CLAUDE.md` '개발 명령어'에 `npm run build:server`와 운용 실행 줄을 더할지 사용자에게 제안합니다.
- 보드에서 묶고 띄우기, PSS 측정, systemd 서비스는 T26·T27에서 합니다.
