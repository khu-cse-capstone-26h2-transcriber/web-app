# [T04] 서버 뼈대(HTTP 서버, `/health`, 에러 처리, pg 연결 풀) — 지침서

2026-10-13 · 이광호

## 목표

`npm run dev:server`를 실행하면 Express 서버가 떠서 계속 요청을 받습니다. `GET /health`로 서버와 DB가 살아 있는지 확인할 수 있고, 없는 경로나 서버 오류는 모두 같은 모양의 JSON으로 응답합니다. Ctrl+C를 누르면 DB 연결을 닫고 끝납니다. 이후의 API(T06~T11)는 이 뼈대에 라우트를 더하는 방식으로 만듭니다.

## 배경과 전제, 범위

`CLAUDE.md`의 확정된 결정에 따라 서버 프레임워크는 Express(D2, 2026-10-12 확정)이고, DB는 `pg`로 직접 SQL을 씁니다. 선행 작업은 T01, T02(모두 완료)입니다. `pg`와 `@types/pg`는 T03에서 이미 설치했으므로 T04에서는 연결 풀만 추가합니다.

실행 전에 루트에 `.env`가 있어야 하고, `/health`가 200을 내려면 `docker compose up -d`로 DB가 떠 있어야 합니다. **2026-10-13 확인 시점에 Docker 데몬이 꺼져 있었습니다. Docker Desktop을 먼저 켭니다.**

- 하는 것: `express`와 `@types/express` 설치, pg 연결 풀, Express 앱(`express.json()`, `GET /health`, 404 처리, 공통 에러 처리), 진입점 교체(listen, 종료 처리).
- 하지 않는 것: 세션 API와 상태 전이(T06), SSE(T07), 세그먼트 저장(T08), 히스토리 API(T10), CORS와 웹앱 연결(T12에서 빌드 도구를 정한 뒤), 요청 로그 미들웨어, 단위 테스트(T17), STT 어댑터를 서버에 붙이는 일(T06).

## 응답 형식

| 요청 | 상태 코드 | 본문 |
| --- | --- | --- |
| `GET /health`, DB 정상 | 200 | `{"status":"ok"}` |
| `GET /health`, DB 연결 실패 | 503 | `{"error":{"code":"DB_UNAVAILABLE","message":"DB에 연결하지 못했습니다"}}` |
| 없는 경로 | 404 | `{"error":{"code":"NOT_FOUND","message":"경로를 찾을 수 없습니다: GET /nope"}}` |
| 본문이 잘못된 JSON | 400 | `{"error":{"code":"INVALID_JSON","message":"요청 본문이 올바른 JSON이 아닙니다"}}` |
| 예상하지 못한 에러 | 500 | `{"error":{"code":"INTERNAL_ERROR","message":"서버에서 오류가 발생했습니다"}}` |

`code`는 프로그램이 구분하는 값(영어 대문자), `message`는 사람이 읽는 설명(한국어)입니다. 500일 때는 실제 에러 내용을 응답에 넣지 않고 서버 로그에만 남깁니다.

4. `apps/server/src/db/pool.ts`에 연결 풀을 만드는 함수를 씁니다.

    ```ts
    // pg 연결 풀을 만든다. 서버 전체가 이 풀 하나를 함께 쓴다.
    import { Pool } from 'pg';

    export function createPool(dbUrl: string): Pool {
      // DB가 꺼져 있을 때 요청이 오래 매달리지 않도록 연결 대기 시간을 둔다.
      const pool = new Pool({ connectionString: dbUrl, connectionTimeoutMillis: 2000 });
      // 쉬고 있던 연결이 끊겨도 프로세스가 죽지 않게 받아서 기록만 한다.
      pool.on('error', (error) => {
        console.error(`[db] 연결 오류: ${error.message || error.name}`);
      });
      return pool;
    }
    ```

5. `apps/server/src/http/errors.ts`에 에러 타입과 미들웨어 두 개를 씁니다.

    ```ts
    // API 에러 응답 형식과 공통 에러 처리. 모든 에러 응답은 { error: { code, message } } 모양이다.
    import type { ErrorRequestHandler, RequestHandler } from 'express';

    // 핸들러에서 던지면 errorHandler가 status와 code를 그대로 응답으로 바꾼다.
    export class HttpError extends Error {
      readonly status: number;
      readonly code: string;

      constructor(status: number, code: string, message: string) {
        super(message);
        this.status = status;
        this.code = code;
      }
    }

    // 어느 라우트에도 걸리지 않은 요청.
    export const notFoundHandler: RequestHandler = (req, res) => {
      res.status(404).json({
        error: { code: 'NOT_FOUND', message: `경로를 찾을 수 없습니다: ${req.method} ${req.path}` },
      });
    };

    // 인자가 넷이어야 Express가 에러 처리 미들웨어로 알아본다.
    export const errorHandler: ErrorRequestHandler = (error, _req, res, _next) => {
      if (error instanceof HttpError) {
        res.status(error.status).json({ error: { code: error.code, message: error.message } });
        return;
      }

      // express.json()이 본문을 읽지 못했을 때.
      if ((error as { type?: unknown }).type === 'entity.parse.failed') {
        res.status(400).json({
          error: { code: 'INVALID_JSON', message: '요청 본문이 올바른 JSON이 아닙니다' },
        });
        return;
      }

      // 예상하지 못한 에러. 내용은 서버 로그에만 남기고 응답에는 넣지 않는다.
      console.error('[server] 처리하지 못한 에러:', error);
      res.status(500).json({
        error: { code: 'INTERNAL_ERROR', message: '서버에서 오류가 발생했습니다' },
      });
    };
    ```

6. `apps/server/src/app.ts`에 앱을 조립합니다.

    ```ts
    // Express 앱을 조립한다. listen은 index.ts에서 한다.
    import express, { type Express } from 'express';
    import type { Pool } from 'pg';
    import { errorHandler, HttpError, notFoundHandler } from './http/errors';

    export function createApp(pool: Pool): Express {
      const app = express();
      app.use(express.json());

      // 서버와 DB가 모두 살아 있는지 확인한다.
      app.get('/health', async (_req, res) => {
        try {
          await pool.query('select 1');
        } catch {
          throw new HttpError(503, 'DB_UNAVAILABLE', 'DB에 연결하지 못했습니다');
        }
        res.json({ status: 'ok' });
      });

      // 라우트 뒤에 둔다. 순서가 바뀌면 모든 요청이 404가 된다.
      app.use(notFoundHandler);
      app.use(errorHandler);
      return app;
    }
    ```

7. `apps/server/src/index.ts`를 아래 내용으로 바꿉니다. `package.json`의 `dev` 스크립트는 고치지 않습니다.

    ```ts
    // 서버 진입점. 환경변수를 읽고 DB 풀과 HTTP 서버를 띄운다.
    import { APP_NAME } from '@app/shared';
    import { createApp } from './app';
    import { loadEnv, maskDbUrl } from './config/env';
    import { createPool } from './db/pool';

    const env = loadEnv();
    const pool = createPool(env.dbUrl);
    const app = createApp(pool);

    // Express 5는 listen에 실패해도 이 콜백을 부르고, 그때 첫 인자로 에러를 준다.
    const server = app.listen(env.port, (error?: Error) => {
      if (error) {
        if ((error as NodeJS.ErrnoException).code === 'EADDRINUSE') {
          console.error(`[server] 포트가 이미 사용 중입니다: ${env.port}`);
        } else {
          console.error(`[server] 시작 실패: ${error.message}`);
        }
        process.exit(1);
      }
      console.log(`[server] ready - ${APP_NAME} http://localhost:${env.port}`);
      // 비밀번호는 가리고 찍는다.
      console.log(
        `[server] config - PORT=${env.port} DB_URL=${maskDbUrl(env.dbUrl)} STT_URL=${env.sttUrl}`,
      );
    });

    // 새 요청을 받지 않고, 처리 중인 요청이 끝나면 DB 풀을 닫고 끝낸다.
    let shuttingDown = false;
    function shutdown(signal: string): void {
      if (shuttingDown) return;
      shuttingDown = true;
      console.log(`[server] ${signal} 받음, 종료합니다`);
      server.close(() => {
        void pool.end().then(() => {
          console.log('[server] 종료 완료');
          process.exit(0);
        });
      });
    }

    process.on('SIGINT', () => shutdown('SIGINT'));
    process.on('SIGTERM', () => shutdown('SIGTERM'));
    ```

## Express 5에서 주의할 점

Express 4에 익숙한 경우 달라진 부분입니다. 이 작업의 코드에 영향을 주는 것만 적습니다.

- **async 핸들러의 에러가 자동으로 전달됩니다.** 핸들러가 `throw`하거나 반환한 Promise가 실패하면 Express가 에러 처리 미들웨어를 부릅니다. Express 4처럼 `try { … } catch (e) { next(e) }`로 감싸지 않아도 됩니다. `/health`가 `HttpError`를 그냥 던지는 것이 이 동작에 기대고 있습니다.
- **`app.listen`의 콜백이 실패 때도 불립니다.** 포트가 이미 쓰이고 있으면 콜백의 첫 인자로 에러가 옵니다. 에러를 확인하지 않으면 실패했는데도 `ready`가 찍힙니다(사전 검증에서 실제로 겪었습니다).
- **경로의 와일드카드 문법이 바뀌었습니다.** `app.get('*', …)`는 동작하지 않고 `'/*이름'` 형태로 써야 합니다. 이 작업에서는 404 처리를 경로 없는 `app.use(notFoundHandler)`로 해서 해당이 없습니다.

## 결정 사항과 남은 질문

- 이미 정한 것: Express, `pg`로 직접 SQL, 위 '착수 전 확인'의 네 가지.
- 이 지침서에서 정한 것:
  - 풀은 모듈 전역 변수로 두지 않고 `createPool(dbUrl)`로 만들어 `createApp(pool)`에 넘깁니다.
  - 풀의 연결 대기 시간은 2초입니다. DB 호스트가 응답하지 않을 때 `/health`가 오래 매달리지 않게 하려는 값이고, 기기에서 실측한 값은 아닙니다.
  - 풀의 최대 연결 수는 `pg` 기본값(10)을 그대로 둡니다. 기기 메모리에 맞춘 조정은 D8(실측 후)에서 합니다.
  - 서버는 호스트를 지정하지 않고 listen합니다. 같은 네트워크의 다른 기기에서도 접속할 수 있습니다. 웹앱을 기기 밖(휴대폰, 노트북)에서 여는 구성을 막지 않기 위해서입니다.
  - 요청 로그는 남기지 않습니다. 필요해지면 그때 추가합니다.
- 아직 정해야 하는 것:
  - 서버를 어느 주소로 열지(모든 인터페이스인지, 특정 주소인지). 기기의 네트워크 구성(D5, 하드웨어 파트 김범수)이 정해지면 다시 봅니다.
  - CORS. 웹앱 빌드 도구(D3)와 개발 서버 구성이 정해지는 T12에서 정합니다.
