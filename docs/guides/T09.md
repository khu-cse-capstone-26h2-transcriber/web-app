# [T09] SSE 재연결 이어받기(`Last-Event-ID`) — 지침서

2026-10-16 · 이광호

## 목표

녹음 중인 세션의 스트림(`GET /api/sessions/:id/events`)이 끊겼다가 다시 이어져도 확정된 문장(final)이 빠지지 않습니다. final에는 SSE `id:`로 `segmentId`가 붙고, 브라우저 `EventSource`는 다시 접속할 때 마지막으로 받은 번호를 `Last-Event-ID`로 보냅니다. 서버는 그 번호 뒤의 final을 먼저 보내고 실시간 이벤트로 이어 갑니다. 헤더 없이 접속하면(새 탭, 새로고침) 그 세션의 final을 처음부터 먼저 보냅니다. T14(실시간 트랜스크립트 화면)는 스트림 하나만으로 화면을 채우고, T15(끊김 처리)는 그 위에 배너와 재접속 정책을 더합니다.

## 배경과 전제, 범위

선행 작업은 T07(SSE 스트림)과 T08(세그먼트 저장)이고 둘 다 끝났습니다. T07은 접속한 뒤의 이벤트만 보냈고, `id:`와 다시 보내기는 이 작업으로 미뤘습니다. 확정된 결정 중 관련된 것은 'SSE로 시작하고 추후 WebSocket 전환을 고려해 설계', 'SSE 끊김은 자동 재연결과 화면 상단 배너'입니다. 실행 전에 Docker Desktop이 켜져 있고 `docker compose up -d`로 DB가 떠 있어야 합니다.

이 지침서는 T06~T08, T10과 같이 구현과 같은 세션에서 썼습니다. 코드 전문은 싣지 않습니다. 코드는 저장소의 파일(커밋 `d000fde`)이 기준이고, 여기에는 결정과 동작, 확인 방법을 적습니다.

- 하는 것: `SseStream`의 `id:` 줄, `SessionManager`가 진행 중인 세션의 final을 모아 두고 접속한 쪽에 먼저 보내기, 라우트에서 `Last-Event-ID` 읽기, 공용 `stream.ts`에 이어받기 규칙 적기.
- 하지 않는 것: 재접속 간격(`retry:`)과 끊김 배너(T15), 웹앱 화면(T14), 끝난 세션의 빠진 문장을 스트림으로 보내기(아래 '착수 전 확인'), 단위 테스트(T17), 스키마 변경.
- 협의가 필요해 가정하지 않는 것: STT 이벤트의 최종 형식(D4, AI 파트 박지윤). 이 작업은 '`segmentId`는 세션 안에서 0부터 늘어난다'는 지금의 초안에 기댑니다. 초안이 바뀌면 `id`를 다시 봅니다.

## 이어받기 동작

| 접속 | 먼저 오는 것 | 그 뒤 |
| --- | --- | --- |
| `Last-Event-ID` 없이 (새 탭, 새로고침, 첫 접속) | 그 세션의 final 전부, 온 순서대로 | 실시간 partial, final, heartbeat, `ended` (T07과 같음) |
| `Last-Event-ID: L` (브라우저가 다시 접속할 때 스스로 보냄) | `segmentId`가 `L`보다 큰 final | 같음 |
| `Last-Event-ID`가 빈 값 | 헤더가 없을 때와 같음 | 같음 |
| `L`이 지금까지의 번호보다 큼 | 없음 | 같음 |
| `L`이 0 이상의 정수가 아님 (`abc`, `-1`, `1.5`, `01`, 안전한 정수 범위 밖) | `400` `INVALID_LAST_EVENT_ID` (에러 JSON) | 없음 |
| 끝난 세션, 없는 번호, 잘못된 세션 번호 | T07과 같이 `409`, `404`, `400`. 세션 번호를 헤더보다 먼저 봅니다 | 없음 |

`id:` 줄은 final에만 붙고 값은 `segmentId`입니다. partial, heartbeat, `ended`에는 붙지 않으므로, 브라우저가 기억하는 번호는 마지막으로 받은 final의 번호로 남습니다.

```text
id: 0
data: {"type":"final","segmentId":0,"text":"안녕하세요 오늘 회의를 시작하겠습니다","startMs":0,"endMs":800}

data: {"type":"partial","segmentId":1,"text":"첫","startMs":800,"endMs":1000}
```

서버 로그의 접속 줄에 먼저 보낸 개수가 붙습니다.

```text
[stream] #27 연결 (지금 1개, final 3개 먼저 보냄)
[stream] #27 연결 (지금 1개, Last-Event-ID 10 뒤 final 3개 먼저 보냄)
```

웹앱이 할 일은 둘입니다. 같은 `segmentId`가 다시 오면 그 줄을 덮어씁니다(T07의 화면 처리와 같음). `ended`를 받으면 `close()`를 부릅니다. 부르지 않아도 다시 접속해 `409`를 받고 멈추지만, 한 번 더 요청이 갑니다.

## 구현 순서

1. DB를 띄우고 `main`에서 새 브랜치를 만듭니다.

    ```bash
    docker compose up -d
    git switch -c feat/t09-sse-resume
    ```

2. `apps/server/src/http/sse.ts`의 `send`가 `id`를 더 받게 합니다. `id`가 있으면 `data` 줄 앞에 `id: <id>` 줄을 씁니다. `SseStream`은 여전히 세션이나 STT를 모릅니다.

3. `apps/server/src/sessions/manager.ts`를 고칩니다.
    - `ActiveSession`에 `finals: SttEvent[]`를 두고, `handleEvent`에서 final이 올 때마다 넣습니다. 저장(`writer`)과는 따로입니다.
    - `subscribe(id, subscriber, afterSegmentId?)`: 진행 중인 세션인지 확인한 뒤, `afterSegmentId`가 없으면 `finals` 전부, 있으면 `segmentId`가 그보다 큰 것만 그 받는 쪽에 보내고, 그다음에 받는 쪽을 등록합니다. 확인부터 등록까지 `await`가 없어 새 이벤트가 끼어들지 않습니다. 먼저 보내다가 예외가 나면 등록되지 않습니다.
    - `SessionSubscriber` 인터페이스는 그대로입니다.

4. `apps/server/src/sessions/routes.ts`를 고칩니다.
    - `parseLastEventId`: 헤더가 없거나 비어 있으면 `undefined`, 0 이상의 정수면 그 값, 아니면 `400` `INVALID_LAST_EVENT_ID`.
    - `sseEventId`: final이면 `String(segmentId)`, 나머지는 `undefined`.
    - 스트림 라우트는 `SseStream`을 감싼 받는 쪽을 만들어 `subscribe`에 넘깁니다. `id`를 붙이는 일은 여기서만 합니다.

    ```ts
    const afterSegmentId = parseLastEventId(req.get('Last-Event-ID'));
    const subscriber: SessionSubscriber = {
      send: (message) => stream.send(message, sseEventId(message)),
      close: () => stream.close(),
    };
    const unsubscribe = await sessions.subscribe(id, subscriber, afterSegmentId);
    ```

5. `packages/shared/src/stream.ts`의 머리 주석에 이어받기 규칙을 적습니다. 웹앱이 같은 규칙을 봅니다.

6. 동작을 확인하고 커밋합니다. push와 `main` 병합은 사용자가 따로 지시할 때 합니다.

    ```bash
    npm run typecheck
    npm run dev:server
    curl -X POST localhost:3000/api/sessions
    curl -N -i localhost:3000/api/sessions/N/events
    curl -N -i -H 'Last-Event-ID: 2' localhost:3000/api/sessions/N/events
    git add packages/shared/src apps/server/src
    git commit -m "feat: SSE 재연결 이어받기(Last-Event-ID) 추가"
    ```

7. 기록을 남깁니다. `docs/logs/`의 그날 일지, `docs/project-overview.md`, `docs/guides/T07.md`의 바뀐 결정, 이 지침서의 '결과'를 채웁니다. `TODO.md`는 변경안을 사용자에게 먼저 보고한 뒤 허락을 받고 고칩니다.

## 결정 사항과 남은 질문

- 이미 정한 것: 위 '착수 전 확인'의 다섯 가지, T07의 스트림 동작(세션별 주소, `data` 안의 `type`, 15초 heartbeat, `ended` 뒤 닫기), final만 저장한다는 것(T08).
- 이 지침서에서 정한 것:
  - **heartbeat와 `ended`에는 `id`를 붙이지 않습니다.** 붙이지 않은 메시지는 브라우저가 기억하는 번호를 바꾸지 않으므로, 그 번호는 늘 '마지막으로 받은 final'입니다.
  - **잘못된 `Last-Event-ID`는 `400` `INVALID_LAST_EVENT_ID`입니다.** 브라우저는 서버가 준 값만 보내므로 손으로 보낸 요청에서만 생깁니다. 무시하고 처음부터 보내는 대신 알리는 쪽을 골랐습니다. 빈 값은 헤더가 없는 것으로 봅니다. 세션 번호를 먼저 확인합니다.
  - **지금까지의 번호보다 큰 값이 오면 먼저 보낼 것이 없습니다.** 에러로 보지 않습니다.
  - **말하던 중이던 partial은 다시 보내지 않습니다.** 다음 partial이 그 문장의 전체 텍스트를 보냅니다. mock에서는 0.2초 안에 옵니다.
  - **final 목록은 온 그대로 모읍니다.** 같은 `segmentId`가 두 번 오면 둘 다 남고 순서대로 다시 보냅니다. 끊기지 않았을 때와 같은 순서이고, 웹앱은 덮어쓰면 됩니다. 지금 초안에서는 생기지 않습니다.
  - **먼저 보낸 뒤에 등록합니다.** 확인부터 등록까지 동기로 처리해 새 이벤트가 끼어들지 않고, 먼저 보내다가 예외가 나도 끊긴 받는 쪽이 등록된 채 남지 않습니다.
  - **`id`는 라우트에서 붙입니다.** `SessionSubscriber`와 `SessionManager`는 SSE를 모릅니다. WebSocket으로 바꾸면 웹앱이 마지막 `segmentId`를 다른 방법(예: 접속 메시지)으로 보내고, 같은 `subscribe(id, subscriber, afterSegmentId)`를 부르면 됩니다.
  - **final 목록에 상한을 두지 않았습니다.** 진행 중인 세션 하나만 들고 있고, 세션이 끝나면 버립니다.
  - **`[stream]` 접속 로그에 먼저 보낸 개수를 더했습니다.**
- 아직 정해야 하는 것:
  - STT 이벤트 형식이 바뀌면 `id`를 다시 봅니다 (D4, AI 파트 박지윤). 지금은 `segmentId`가 세션 안에서 0부터 늘어난다는 초안에 기댑니다. STT가 앞 세그먼트의 final을 나중에 고쳐 보내는 방식이 되면 브라우저의 번호가 뒤로 돌아가 다음 재접속 때 몇 문장이 겹쳐 옵니다(덮어쓰면 화면은 같음).
  - final 목록의 메모리. 1시간 녹음에 1MB 미만으로 예상하지만 재지 않았습니다. Rubik Pi 실측(T21) 때 봅니다.
  - 재접속 간격(`retry:`)과 끊김 배너 (T15). 지금은 브라우저 기본값(확인한 브라우저에서 약 3초)입니다.
  - 끊긴 사이에 세션이 끝났거나 종료를 처리하는 중(`stopping`)이면 재접속이 `409`입니다. 웹앱이 이때 상세 API(T10)로 남은 문장과 상태를 받는 처리를 T15에서 합니다.
  - T06~T10에서 넘어온 것은 그대로입니다: 물리 버튼으로 시작한 녹음을 웹앱이 알아채는 방법(D4, 하드웨어 파트 김범수), 세션 API의 500을 503으로 맞출지(T13 전), 강제로 꺼진 세션의 `ended_at` 보정(T16 전), 정지할 때 말하던 문장(D4의 C3), 저장 대기열 상한(T21), 동시 접속 수 상한(T21).
