# [T15] SSE 끊김 처리(자동 재연결, 상단 배너) — 지침서

2026-10-23 · 이광호

## 목표

녹음 화면의 실시간 자막 스트림이 끊기면, 화면 맨 위에 배너를 띄우고 스스로 다시 연결합니다. 다시 연결되면 `다시 연결되었습니다`를 잠깐 보여 주고 배너를 숨깁니다. 끊긴 사이에 녹음이 끝났으면(기기 버튼으로 종료, 서버 재시작으로 중단) 다시 연결하는 대신 히스토리 상세로 넘어갑니다. 화면 위쪽의 서버 상태도 30초마다, 그리고 스트림이 다시 연결될 때 다시 확인해, 서버가 다시 켜지면 새로고침하지 않아도 `정상`으로 돌아옵니다.

## 배경과 전제, 범위

선행 작업 T14(실시간 트랜스크립트 화면)는 끝났습니다. 실행 전에 Docker Desktop이 켜져 있고 `docker compose up -d`로 DB가 떠 있어야 하며, 루트 `.env`가 있어야 합니다.

T14까지는 끊겼을 때의 재연결을 `EventSource` 기본 동작에 맡겼습니다. 그런데 `EventSource`에는 두 가지 한계가 있습니다.

- 200이 아닌 응답을 받으면 다시 접속하지 않고 멈춥니다. 끊긴 사이에 세션이 끝나 받는 `409`, 개발 중 서버가 꺼졌을 때 Vite 프록시가 주는 `502`가 여기에 해당합니다(Vite는 프록시 대상에 닿지 못하면 `502`로 답합니다).
- 응답 코드를 화면 코드에 알려 주지 않습니다. `409`와 `502`가 똑같은 `error` 이벤트로 보입니다.

그래서 T15에서는 다시 연결을 웹앱이 직접 맡고, 끊긴 뒤에는 `GET /api/sessions/active`로 세션 상태를 따로 물어봅니다.

- 하는 것: 스트림 훅의 끊김 감지와 다시 연결, 녹음 화면 맨 위의 연결 배너와 '지금 다시 연결' 버튼, 끊긴 사이에 녹음이 끝났을 때 히스토리 상세로 이동, 위쪽 서버 상태 다시 확인.
- 하지 않는 것: 서버와 `packages/shared` 변경(`retry:` 줄 포함), 끊긴 사이에 다른 곳에서 새로 시작한 녹음으로 옮겨 가는 것(D4 뒤), 히스토리 화면(T16), 디자인, 단위 테스트(T17).

## 구현 순서

1. Docker Desktop을 켜고 DB를 띄운 뒤 `main`에서 새 브랜치를 만듭니다.

    ```bash
    docker compose up -d --wait
    git switch -c feat/t15-sse-reconnect
    ```

2. `useSessionStream.ts`를 고칩니다. 구독 하나(세션 번호 하나) 안에서 다음을 합니다.
    - 스트림을 열 때와 메시지·`open`이 올 때마다 30초 무소식 타이머를 다시 겁니다.
    - `error`나 무소식이면 스트림을 닫고 시도 번호를 하나 올린 뒤, 간격만큼 기다렸다가 `GET /api/sessions/active`를 부릅니다. 이 요청은 5초가 지나면 취소하고 실패로 봅니다(서버가 멈춰 답하지 않을 때 기다리지 않도록).
    - 답이 같은 세션이면 스트림을 새로 엽니다. `open`이 오면 `{ status: 'open', reconnected: true }`로 바꾸고 시도 번호를 0으로 되돌립니다.
    - 답이 `null`이거나 다른 세션이면 스트림과 타이머를 모두 멈추고 `onEnded(sessionId)`를 부릅니다.
    - `ended`를 받으면 T14와 같이 먼저 닫고 `onEnded(sessionId)`를 부릅니다.
    - 화면을 떠나거나 세션 번호가 바뀌면 스트림, 타이머, 진행 중인 요청을 모두 멈춥니다.

3. `ConnectionBanner.tsx`를 씁니다. `reconnecting`이면 끊김 문구와 버튼, `open`이고 `reconnected`이면 회복 문구를 3초 보입니다. `position: sticky; top: 0`으로 스크롤해도 위에 붙어 있게 합니다.

4. `useServerHealth.ts`를 쓰고 `Layout.tsx`의 서버 상태를 바꿉니다. 확인이 끝날 때마다가 아니라 확인을 시작할 때 다음 확인을 30초 뒤로 예약하고, 다음 확인이 시작되면 앞의 요청을 취소해 요청이 겹치지 않게 합니다. `Outlet`에 `{ recheckServer }`를 context로 넘깁니다.

5. `RecordPage.tsx`에서 `useOutletContext`로 `recheckServer`를 받아, 스트림이 다시 연결되면 부릅니다. 맨 위(제목 위)에 `ConnectionBanner`를 둡니다.

6. 동작을 확인하고 커밋합니다. 서버를 멈추는 확인은 아래 '완료 기준'을 따릅니다. Vite를 껐다 켜는 확인은 `npm run preview -w @app/web`(4173)로 합니다. 개발 서버(5173)는 Vite가 다시 켜지면 페이지를 새로고침해 끊김 처리를 확인할 수 없습니다.

    ```bash
    npm run typecheck
    npm run build -w @app/web
    git add apps/web/src docs/guides/T15.md
    git commit -m "feat: 실시간 자막 끊김 배너와 자동 재연결 추가"
    ```

7. 기록을 남깁니다. `docs/logs/`의 그날 일지, `docs/project-overview.md`, 이 지침서의 '결과'를 채웁니다. `TODO.md`는 변경안을 사용자에게 먼저 보고한 뒤 허락을 받고 고칩니다.

## 완료 기준

## 결정 사항과 남은 질문

- 이미 정한 것: 위 '착수 전 확인', 스트림 메시지 형식과 이어받기(T07, T09), 녹음 화면과 자막(T13, T14).
- 구현하면서 정하는 것:
  - **진행 중인 세션을 물어보는 요청은 5초가 지나면 실패로 봅니다.** 서버가 멈춰 답하지 않으면 시도가 끝나지 않기 때문입니다.
  - **처음 접속에 실패해도 끊긴 것과 같게 다룹니다.** 배너가 나오고 다시 시도합니다.
  - **서버가 종료를 처리하는 중(`stopping`)에는 `active`가 그 세션을 돌려주지만 스트림은 `409`입니다.** 이때는 시도가 몇 번 실패하다가 종료가 끝나면 히스토리 상세로 갑니다. 따로 처리하지 않습니다.
  - **`recheckServer`는 `Outlet` context로 넘깁니다.** 배너와 서버 상태가 다른 컴포넌트에 있어도 전역 상태를 새로 두지 않습니다.
- 아직 정해야 하는 것:
