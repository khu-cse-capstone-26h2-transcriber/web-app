# [T08] 세그먼트 DB 저장(partial/final 구분) — 지침서

2026-10-14 · 이광호

## 목표

녹음 중에 STT가 final 이벤트를 낼 때마다 그 세그먼트가 `segments` 테이블에 한 행으로 들어갑니다. partial은 저장하지 않습니다. 녹음 중에 DB가 잠깐 꺼져도 그동안의 final은 메모리에 남았다가 DB가 돌아오면 순서대로 저장됩니다. 세션을 종료하면 그 세션의 final이 모두 DB에 있습니다. T10(히스토리 API)은 이 행을 읽어서 만듭니다.

## 배경과 전제, 범위

선행 작업은 T03(스키마)과 T06(세션 API)이고 모두 끝났습니다. `segments` 테이블은 T03에서 만든 그대로 쓰고, 이벤트는 T06의 `SessionManager.handleEvent`에서 받습니다. 실행 전에 Docker Desktop이 켜져 있고 `docker compose up -d`로 DB가 떠 있어야 합니다.

이 지침서는 T06과 같이 구현과 같은 세션에서 썼습니다. 코드 전문은 싣지 않습니다. 코드는 저장소의 파일(커밋 `21b7d82`)이 기준이고, 여기에는 결정과 동작, 확인 방법을 적습니다.

- 하는 것: `segments` 테이블에 쓰는 SQL, 세션의 final을 순서대로 쓰고 실패하면 다시 시도하는 `SegmentWriter`, `SessionManager`에서 final을 넘기고 종료 전에 밀린 것을 쓰는 연결.
- 하지 않는 것: 마이그레이션(스키마는 바꾸지 않음), 세그먼트를 읽는 API와 공용 `Segment` 타입(T10), SSE(T07), 단위 테스트(T17), 강제로 꺼진 세션의 `ended_at` 보정(T06의 남은 질문, 아직 미정).
- 협의가 필요해 가정하지 않는 것 (D4, AI 파트 박지윤):
  - 정지할 때 말하던 문장(C3). 지금은 final이 오지 않은 세그먼트는 저장되지 않습니다. mock으로 녹음하다 문장 중간에 종료하면 그 문장은 DB에 없습니다. STT가 정지 때 마지막 final을 내주는지가 정해지면 다시 봅니다.
  - 같은 세그먼트의 final이 다시 오는지(E6). 어느 쪽이어도 동작하도록 덮어쓰기로 만들었습니다.

## 저장 동작

| 상황 | 일어나는 일 |
| --- | --- |
| partial이 옴 | 개수만 셉니다. DB에 쓰지 않습니다 |
| final이 옴 | 메모리의 대기열 끝에 넣고 바로 씁니다. 한 행이 `(session_id, segment_id, text, start_ms, end_ms)`입니다 |
| 같은 `(세션, segmentId)`의 final이 또 옴 | 같은 행의 `text`, `start_ms`, `end_ms`를 나중 값으로 바꿉니다 |
| DB에 닿지 못해 쓰기가 실패함 | 대기열 맨 앞에 그대로 두고 멈춥니다. `[segment] #N 저장 실패, 메모리에 두고 다시 시도합니다: …`를 한 번 찍습니다. 뒤에 오는 final은 대기열에 쌓입니다 |
| 다음 final이 옴 (DB가 돌아옴) | 대기열 맨 앞부터 순서대로 씁니다. 모두 쓰면 `[segment] #N 밀린 세그먼트를 모두 저장했습니다`를 찍습니다 |
| 종료 요청 | STT를 멈추고, 대기열을 모두 쓴 뒤에 세션을 `ended`로 닫습니다 |
| 종료 요청, DB에 닿지 못함 | `stop`이 500을 내고 세션은 녹음 중으로 남습니다. STT는 이미 멈춰 있습니다. DB가 돌아온 뒤 다시 `stop`을 보내면 대기열을 쓰고 닫습니다 |
| 서버 종료(Ctrl+C, `SIGTERM`) | 대기열을 한 번 써 봅니다. 쓰지 못하면 `[segment] #N 저장하지 못한 세그먼트 K개를 잃었습니다`를 찍고 끝냅니다 |
| 서버가 강제로 꺼짐(`kill -9`) | 그때까지 쓴 행은 DB에 남습니다. 대기열에 있던 것은 잃습니다 |
| DB가 그 행을 거절함 (값이나 제약 오류, SQLSTATE가 22나 23으로 시작) | 다시 써도 같은 결과이므로 그 세그먼트는 버리고 `[segment] #N 세그먼트 M번을 DB가 거절해 버립니다: …`를 찍습니다. 뒤의 세그먼트는 계속 씁니다 |

종료 로그에 저장한 개수가 붙습니다: `[session] #N 종료 - partial 25개, final 7개, 저장 7개`. `저장`이 `final`보다 작으면 버린 세그먼트가 있다는 뜻입니다.

## 구현 순서

1. DB를 띄우고 `main`에서 새 브랜치를 만듭니다.

    ```bash
    docker compose up -d
    git switch -c feat/t08-segment-storage
    ```

2. `apps/server/src/segments/repository.ts`에 `upsertSegment(pool, sessionId, event)`를 씁니다. final 이벤트 하나를 한 행으로 쓰고, 같은 `(session_id, segment_id)`가 있으면 덮어씁니다.

    ```sql
    insert into segments (session_id, segment_id, text, start_ms, end_ms)
    values ($1, $2, $3, $4, $5)
    on conflict (session_id, segment_id)
    do update set text = excluded.text, start_ms = excluded.start_ms, end_ms = excluded.end_ms
    ```

3. `apps/server/src/segments/writer.ts`에 `SegmentWriter`를 씁니다. 세션마다 하나씩 만듭니다.

    | 멤버 | 하는 일 |
    | --- | --- |
    | `enqueue(event)` | final을 대기열 끝에 넣고 바로 써 봅니다. 실패해도 던지지 않습니다 |
    | `flush()` | 대기열을 모두 쓸 때까지 기다립니다. 쓰지 못하면 던지고, 대기열은 그대로 남습니다 |
    | `savedCount` | DB에 쓴 세그먼트 개수 |
    | `pendingCount` | 아직 쓰지 못해 메모리에 남은 개수 |

    쓰기는 한 번에 하나만 돌립니다. 맨 앞의 것을 쓰고, 성공하면 대기열에서 빼고 다음 것을 씁니다. 그래서 DB에 들어가는 순서가 이벤트가 온 순서와 같습니다.

4. `apps/server/src/sessions/manager.ts`를 고칩니다.
    - `ActiveSession`에 `writer`를 두고, 세션을 만들 때 `new SegmentWriter(this.pool, session.id)`로 만듭니다.
    - `handleEvent`에서 final이면 `active.writer.enqueue(event)`를 부릅니다.
    - `stop`에서 어댑터를 멈춘 뒤, `closeSession` 앞에 `await active.writer.flush()`를 둡니다. 던지면 T06의 처리 그대로 상태가 `recording`으로 돌아갑니다.
    - `shutdown`에서 어댑터를 멈춘 뒤 `flush()`를 한 번 부르고, 실패하면 잃은 개수를 로그로 남깁니다.
    - 종료·중단 로그에 `저장 N개`를 붙입니다.

5. 동작을 확인하고 커밋합니다. push와 `main` 병합은 사용자가 따로 지시할 때 합니다.

    ```bash
    npm run typecheck
    npm run dev:server
    curl -X POST localhost:3000/api/sessions
    curl -X POST localhost:3000/api/sessions/N/stop
    docker compose exec db psql -U user -d transcriber -c 'select * from segments where session_id = N order by segment_id'
    git add apps/server/src/segments apps/server/src/sessions/manager.ts
    git commit -m "feat: final 세그먼트 DB 저장과 재시도 추가"
    ```

6. 기록을 남깁니다. `docs/logs/`의 그날 일지, `docs/project-overview.md`, 이 지침서의 '결과'를 채웁니다. `TODO.md`는 변경안을 사용자에게 먼저 보고한 뒤 허락을 받고 고칩니다.

| 명령어 | 기대 출력 |
| --- | --- |
| `npm run typecheck` | tsc 에러 없이 종료 코드 0 |

| 녹음 중에 `docker compose stop db` | 서버 로그에 `[segment] #N 저장 실패, 메모리에 두고 다시 시도합니다: …`가 한 번. 서버는 떠 있음 |

## 결정 사항과 남은 질문

- 이미 정한 것: 위 '착수 전 확인'의 세 가지, final만 저장한다는 것(T03, T05), T06의 종료 순서(STT를 먼저 멈추고 DB를 닫음)와 종료 재요청.
- 이 지침서에서 정한 것:
  - **final이 올 때마다 바로 한 행씩 씁니다.** 모아서 한꺼번에 쓰지 않습니다. 서버가 강제로 꺼져도 마지막으로 쓴 final까지는 남습니다.
  - **쓰기는 세션마다 한 번에 하나, 온 순서대로입니다.** 앞의 것을 쓰지 못하면 뒤의 것도 쓰지 않습니다.
  - **재시도는 다음 final이 올 때, 종료를 요청할 때, 서버를 끌 때 합니다.** 타이머로 따로 재시도하지 않습니다. 종료 요청이 실패한 뒤에는 STT가 멈춰 final이 더 오지 않으므로, 종료를 다시 요청해야 대기열이 써집니다.
  - **대기열에 상한을 두지 않았습니다.** 한 행이 문장 하나라 작지만, DB가 오래 꺼져 있으면 계속 쌓입니다.
  - **DB가 거절한 행은 버립니다.** 값이나 제약 오류(SQLSTATE 22, 23)는 다시 써도 같아서, 남겨 두면 뒤의 세그먼트와 세션 종료를 영영 막습니다. 사용자가 정한 '재시도'는 DB에 닿지 못한 경우에만 적용했습니다.
  - **서버를 끌 때 쓰지 못한 세그먼트는 잃습니다.** 디스크에 따로 적어 두지 않습니다.
  - **공용 `Segment` 타입은 만들지 않았습니다.** 쓰는 쪽은 `SttEvent`를 그대로 받습니다. 읽는 API를 만드는 T10에서 추가합니다.
  - **스키마는 바꾸지 않았습니다.** T03의 `segments` 그대로입니다.
- 아직 정해야 하는 것:
  - 정지할 때 말하던 문장을 어떻게 할지 (D4의 C3, AI 파트 박지윤). 지금은 final이 오지 않은 세그먼트는 저장되지 않습니다.
  - 같은 세그먼트의 final이 다시 올 수 있는지 (D4의 E6, AI 파트 박지윤). 덮어쓰기로 만들어 두어 어느 쪽이어도 코드는 그대로입니다.
  - 대기열의 상한. Rubik Pi의 메모리를 재는 T21 때 봅니다.
  - T06에서 넘어온 두 가지는 그대로 남아 있습니다: DB가 꺼져 있을 때 세션 API의 500을 503으로 맞출지(T13 전), 강제로 꺼진 세션의 `ended_at`을 마지막 세그먼트 시각으로 보정할지.
