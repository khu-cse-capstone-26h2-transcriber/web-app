# [T32] SIGTERM 멈춤 고치기 — 지침서

2026-11-14 · 이광호

## 목표

녹음 중에 브라우저가 녹음 화면을 열어 두어도 서버가 SIGTERM(그리고 SIGINT)으로 끝나게 합니다. 끝나면 아래가 됩니다.

1. 녹음 중에 SIGTERM을 받으면 진행 중인 세션을 곧바로 중단(`interrupted`)으로 닫습니다. 밀린 final은 지금처럼 마지막으로 한 번 써 봅니다.
2. 브라우저가 열려 있어도 10초 안에 `[server] 종료 완료`가 찍히고 프로세스가 끝납니다.
3. 종료가 시작된 뒤에는 웹앱이 SSE에 다시 붙지 못합니다(`[stream] #N 연결` 줄이 다시 찍히지 않음).
4. 녹음이 없을 때와 브라우저가 없을 때의 종료는 지금과 같습니다.

## 배경과 전제, 범위

- T21(2026-11-13) 9단계에서 찾은 문제입니다. 원인은 `docs/guides/T21.md` '원인 분석 (2026-11-14)'의 1절에 있습니다. 요약하면 다음과 같습니다.
  - `apps/server/src/index.ts`의 `shutdown()`은 `server.close()` → SSE만 끊음(`disconnectSubscribers`) 순서이고, 세션 정리(`sessions.shutdown()`)는 `close` 콜백 안에서만 돕니다.
  - Node 22의 `server.close()`는 그 순간 쉬고 있는 연결만 닫습니다. SSE가 쓰던 소켓은 그때 쓰는 중이라 남고, SSE가 끝난 뒤에는 keep-alive로 남습니다.
  - 웹앱은 1초 뒤 그 소켓으로 `/api/sessions/active`를 묻고, 세션이 아직 `recording`이라 SSE를 다시 엽니다. `SessionManager.subscribe`는 이 구독을 받습니다.
  - `close` 콜백은 연결이 모두 닫혀야 불리고, 이 연결은 세션이 끝나야 닫히고, 세션은 `close` 콜백에서 끝납니다. 서로를 기다려 멈춥니다.
- 보드에서만 드러난 것은 보드에서 Express가 웹앱을 직접 내보내기(T31) 때문입니다. 노트북 개발 방식은 Vite 프록시가 새 연결을 맺어 드러나지 않았습니다(기록상, 다시 확인하지 않음). 그래서 이번에는 노트북에서도 Vite를 거치지 않고 `localhost:3000`으로 확인합니다.
- systemd로 서버를 끄거나 다시 켤 때(T26·T27) 이대로면 기본 90초(`TimeoutStopSec`) 동안 멈췄다가 강제 종료됩니다. 그동안 녹음이 계속됩니다. 자동 시작 전에 고칩니다.

- 하는 것: 서버 종료 순서 변경(세션 먼저 중단), 남은 연결을 끊는 안전장치, 쓰지 않게 되는 `disconnectSubscribers` 정리, 관련 문서.
- 하지 않는 것: 종료 중 `503` 응답(분석의 (나)), `SessionManager`의 시작 막기, 웹 코드 변경, keep-alive 시간(`keepAliveTimeout`) 변경, systemd 서비스(T26·T27), 보드에서 확인(T26으로 넘김), 실행 방식 정리(`npm run` 묶음, T21 찾은 문제 5), 단위 테스트(핵심 로직이 아님, CLAUDE.md 규칙).

## 동작

| 상황 | 지금 | 고친 뒤 |
| --- | --- | --- |

| 녹음 중, 브라우저가 녹음 화면 | 끝나지 않음. SSE가 다시 붙고 녹음이 계속됨 | `#N 중단 (서버 종료)`가 바로 찍힘. 웹앱은 1초 뒤 다시 시도할 때 남은 연결로 '진행 중인 세션 없음'을 받아 상세 화면(`중단됨`)으로 감. 그 연결이 keep-alive로 남아 5초 뒤 안전장치가 끊고 `종료 완료` |
| 위와 같은데 브라우저가 새 연결로 다시 시도함 | (해당 없음) | 연결 거부로 끊김 배너(T15). 서버는 위와 같이 끝남 |
| 종료 중 남은 연결로 새 세션이 시작됨 | (해당 없음) | 5초 안전장치 뒤 두 번째 `sessions.shutdown()`이 중단으로 닫음. DB에 `recording`으로 남지 않음 |

브라우저 쪽이 상세 화면으로 갈지 끊김 배너를 띄울지는 브라우저가 연결을 다시 쓰는지에 달려 있습니다. 둘 다 통과로 보고, 어느 쪽이었는지 기록합니다.

## 구현 방향

`index.ts`의 `shutdown()`을 아래 모양으로 바꿉니다. 이름과 문구는 구현하면서 다듬을 수 있습니다.

```ts
// 브라우저가 keep-alive 연결을 놓지 않아도 이 시간(ms)이 지나면 남은 연결을 끊는다. systemd 기본 90초보다 훨씬 짧게.
const FORCE_CLOSE_MS = 5_000;

let shuttingDown = false;
function shutdown(signal: string): void {
  if (shuttingDown) return;
  shuttingDown = true;
  console.log(`[server] ${signal} 받음, 종료합니다`);
  // 세션을 먼저 중단한다. 첫 await 전에 진행 중인 세션을 비우고 SSE를 닫으므로,
  // 다시 붙으려는 웹앱은 '진행 중인 세션 없음'을 받는다. (T32)
  const sessionsClosed = closeSessions();
  const serverClosed = new Promise<void>((resolve) => server.close(() => resolve()));
  const forceTimer = setTimeout(() => {
    console.log(`[server] ${FORCE_CLOSE_MS / 1000}초 안에 닫히지 않은 연결을 끊습니다`);
    server.closeAllConnections();
  }, FORCE_CLOSE_MS);
  void Promise.all([sessionsClosed, serverClosed])
    // 종료 중에 남은 연결로 새 세션이 시작됐을 수 있어 한 번 더 닫는다.
    .then(() => closeSessions())
    .then(() => {
      clearTimeout(forceTimer);
      return pool.end();
    })
    .then(() => {
      console.log('[server] 종료 완료');
      process.exit(0);
    });
}

function closeSessions(): Promise<void> {
  return sessions.shutdown().catch((error: unknown) => {
    console.error('[session] 진행 중인 세션을 닫지 못했습니다:', error);
  });
}
```

- `server.close()`는 서버가 이미 닫혀 있으면 콜백에 에러를 줍니다. 그때도 종료를 이어 가도록 콜백 인자는 보지 않습니다.
- `pool.end()`는 두 번째 세션 정리까지 끝난 뒤에 부릅니다. 세션을 닫으려면 DB가 필요합니다.

## 확인하지 않는 것

- 보드에서의 동작과 systemd로 끄기: T26에서 서비스로 띄울 때 같은 절차로 확인합니다.
- 실제 엔진(`STT_MODE=local`)으로 녹음 중일 때의 종료: 어댑터를 멈추는 데 최대 5초가 걸려도 안전장치는 연결만 끊으므로 세션은 끝까지 닫힙니다. 이번에는 mock으로만 확인합니다.
- 종료 중 새 세션이 시작되는 경우: 일부러 만들기 어려워 실행으로 확인하지 않고 코드로만 봅니다.

## 결정 사항과 남은 질문

- 이미 정한 것: 위 '착수 전 확인'.
- 녹음 화면이 열려 있으면 종료에 약 5초가 걸립니다. 더 줄이려면 세션을 닫은 뒤 쉬는 연결을 바로 닫으면 되지만(`closeIdleConnections`), 그러면 웹앱이 상세 화면 대신 끊김 배너를 보게 됩니다. 이번에는 고르지 않습니다.
- T26·T27에서 정할 것: systemd의 `TimeoutStopSec`를 기본값으로 둘지. 이 작업 뒤에는 기본 90초 안에 끝납니다.
