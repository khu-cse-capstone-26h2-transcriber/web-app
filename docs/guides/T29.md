# [T29] 기기 수신 경로(web-app PR #1) 노트북 실제 모델 시험 — 지침서

2026-11-09 · 이광호

## 목표

기기에 올리기 전에 노트북에서 AI 파트의 실제 엔진(`stt-engine`, ONNX)과 web-app PR #1의 기기 수신 경로(`/api/device/sessions`)를 잇습니다. 그래서 WAV 입력이 실시간 자막, DB, 히스토리, 내보내기까지 이어지는지, 끝·오류·세션 교체 때 앱이 정한 대로 처리하는지 확인합니다. 결과는 PR #1 의견, T19 협의(하드웨어 요청의 근거), T20·T26 준비에 씁니다.

## 배경과 전제, 범위

- T28(2026-11-03)은 우리가 만든 `stream_engine.py`를 서버가 띄우는 방식 B였습니다. T29는 AI 파트의 실제 엔진 코드(구간 나누기, 2초 partial, 빈 final, `session_done`)와 방식 A의 HTTP 수신 경로를 씁니다.
- 연결은 web-app PR #1의 `docs/device-ingest.md`와 같습니다.

    ```text
    feed_wav.py(데몬 대신) ─AUDIO→ board_stream.py + fake_runner.py(ONNX) ─RESULT→ feed_wav.py ─HTTP→ 서버 /api/device/sessions ─SSE→ 웹
    ```

- `feed_wav.py`(audio-stack PR #2, `a775c37`)는 데몬과 다릅니다. 코드를 읽어 확인한 점은 다음과 같습니다.
  - HTTP 응답 코드를 보지 않고 다시 보내지 않습니다. 실패는 표준 오류에 로그만 남깁니다.
  - 세션 교체가 없습니다. 엔진이 접속할 때 세션 하나를 열고, 파일이 끝나면 닫습니다.
  - `SESSION_END` 뒤 엔진이 끝날 때까지(최대 30초) 기다린 다음 `/end`를 보냅니다. 그래서 지금 데몬과 달리 마지막 final이 `/end`보다 먼저 옵니다.
  - POST는 오디오를 보내는 같은 흐름에서 3초 제한으로 보냅니다. 서버가 느리면 오디오도 밀립니다.
  - 그래서 재전송, 세션 교체, 늦은 결과는 curl로 서버만 따로 시험합니다.
- 실제 `audiostackd`는 Linux와 `snd-aloop`이 필요해 Mac에서 돌리지 않습니다.
- Mac 엔진은 양자화 전 ONNX 모델(인코더 387 MB, 디코더 684 MB)을 onnxruntime CPU로 돌립니다. 정확도와 지연은 보드 값이 아닙니다. 실시간을 따라가지 못하면 지연이 커지고 partial을 건너뜁니다. 합격선 없이 기록만 합니다.
- PR #1은 박지윤의 초안입니다(`7b0c408`, 병합 전). 이 작업은 PR 코드를 고치지 않습니다.

범위는 다음과 같습니다.

- 하는 것: 저장소 밖 준비(클론, 모델, 가상환경), PR #1 코드를 별도 워크트리에 받기, 시험용 DB, 아래 '완료 기준'의 시험, 결과 기록.
- 하지 않는 것: 서버·웹·공용 코드 변경(이 저장소와 PR 모두), PR 코멘트(결과를 보고 사용자 확인 뒤 따로), 실제 데몬과 보드(T26, T27), 마이크, `main` 병합, 단위 테스트 추가.

## 시험 순서

1. 준비합니다(1일차). 메인 체크아웃에서 DB와 워크트리를 만듭니다.

    ```bash
    docker compose up -d --wait
    docker compose exec db createdb -U user transcriber_pr1
    git fetch origin pull/1/head
    git worktree add --detach ~/Desktop/stt-lab/web-app-pr1 7b0c408
    ```

    저장소 밖에 엔진, 데몬 도구, 모델을 받습니다. ONNX는 약 1.1 GB입니다.

    ```bash
    cd ~/Desktop/stt-lab
    gh repo clone khu-cse-capstone-26h2-transcriber/stt-engine
    gh repo clone khu-cse-capstone-26h2-transcriber/audio-stack
    git -C audio-stack fetch origin pull/2/head && git -C audio-stack checkout --detach a775c37
    /opt/homebrew/bin/python3.12 -m venv engine-venv && engine-venv/bin/pip install numpy onnxruntime
    mkdir -p onnx && gh release download v0.1 -R khu-cse-capstone-26h2-transcriber/stt-engine -p '*.onnx' -p SHA256SUMS -D onnx
    ```

    워크트리에 `.env`를 두고(`DB_URL`의 DB 이름만 `transcriber_pr1`), `nvm use`, `npm ci`, `npm run typecheck`, `npm test`, `npm run db:migrate`를 차례로 실행합니다.

2. 엔진만 돌려 봅니다. 백엔드 없이 `feed_wav.py`와 엔진을 띄워 final과 `session_done`이 나오는지 봅니다.

    ```bash
    # 터미널 1 (stt-lab)
    engine-venv/bin/python audio-stack/tools/feed_wav.py stt-engine/samples/fleurs_ko_30s.wav --socket /tmp/astk/engine.sock
    # 터미널 2 (stt-lab/stt-engine)
    WHISPER_RUNNER="../engine-venv/bin/python fake_runner.py" ../engine-venv/bin/python board_stream.py \
      --astk /tmp/astk/engine.sock --once --bins ../onnx --cut early --partial 2
    ```

3. 기본 흐름을 봅니다. 워크트리에서 `npm run dev:server`와 `npm run dev:web`을 띄우고 녹음 화면을 열어 둔 채, 2단계에 `--backend-url http://localhost:3000 --backend-prefix /api/device/sessions`를 붙여 다시 실행합니다. 끝나면 히스토리에서 txt와 md를 내려받고 psql로 행을 셉니다.
4. 엔진 결과 처리를 봅니다. partial 모양, 빈 final(`--lp-min -0.5`와 `t29_noise.wav`), 숫자와 문장부호, `demo_long.wav`를 차례로 돌립니다.
5. 시작·종료 순서를 봅니다(2일차). 웹 '녹음 종료', mock 녹음 중 기기 세션, 새로고침과 다른 탭입니다.
6. 오류와 끊김을 봅니다. 서버 `SIGINT`, Vite `SIGSTOP`, 엔진 강제 종료입니다.
7. curl로 데몬 동작을 흉내 냅니다. 아래 '완료 기준'의 순서대로 보냅니다. 서버만 띄우고 엔진은 쓰지 않습니다.

    ```bash
    B=http://localhost:3000/api/device/sessions
    curl -s -w ' %{http_code}\n' -H 'Content-Type: application/json' -d '{"session_id":"sess-curl-a"}' $B
    curl -s -w ' %{http_code}\n' -H 'Content-Type: application/json' \
      -d '{"seq":1,"transcript":{"type":"final","text":"첫 문장","t_start_ms":0,"t_end_ms":1500}}' $B/sess-curl-a/transcripts
    ```

8. 정리합니다. 남은 프로세스를 확인하고, 메인 체크아웃과 개발 DB가 그대로인지 봅니다. 워크트리와 시험용 DB는 결과를 정리할 때까지 둡니다.
9. 기록을 남깁니다. `~/Desktop/stt-lab/README.md`, 그날 일지, 이 지침서의 '결과'를 채웁니다. `TODO.md`는 변경안을 사용자에게 먼저 보고한 뒤 허락을 받고 고칩니다.

## 완료 기준

'기록'이라고 적은 줄은 합격선이 없고 값과 모습을 적습니다. 기대 출력은 PR #1(`7b0c408`)과 `feed_wav.py`(`a775c37`) 코드를 읽어 예상한 것입니다. 다르게 나오면 그대로 기록하고, 고칠 일인지는 사용자와 정합니다.

### 준비 (1일차)

| 명령어·동작 | 기대 출력 |
| --- | --- |
| 워크트리 `npm run typecheck`, `npm test` | 종료 코드 0, 테스트 42개 통과 |
| 워크트리 `npm run db:migrate` | `003_device_session.sql` 적용. 개발 DB `transcriber`의 `schema_migrations`에는 `003`이 없음 |

### 기본 흐름 (1일차, fleurs)

| 명령어·동작 | 기대 출력 |
| --- | --- |
| 녹음 화면을 열어 두고 3단계 실행 | 서버 로그 `[device] 세션 sess-feed-… → #N`. 버튼을 누르지 않아도 2초 안에 `녹음 중`. 걸린 시간 기록 |
| 녹음 중 화면 | 흐린 줄이 바뀌고 final이 쌓임 |
| 오디오가 끝남 | 엔진 `session_done` 뒤 `/end`, 세션 `ended`, 웹이 `/history/N`으로 이동. 오디오 끝부터 이동까지 걸린 시간 기록 |
| 개수 | 엔진 `session_done`의 `finals`에서 빈 final 수를 뺀 값 = 서버 로그 final 수 = 화면 문장 수 = psql 행 수 |
| 번호와 시각 | psql `segment_id`가 0부터 빈틈없음. `start_ms`·`end_ms`가 엔진 로그 final 줄의 `[s~e s]`와 0.1초 안에서 같음 |
| txt·md 내려받기 | 둘 다 받아지고 문장 수가 화면과 같음. CER 기록 |

### 엔진 결과 처리 (1일차)

| 명령어·동작 | 기대 출력 |
| --- | --- |
| partial 모양 | 기록: partial 수, 건너뛴 partial 수(엔진 끝 요약 `PARTIAL … skipped`), 그 구간 final과 앞부분이 절반 넘게 다른 partial 수(T28은 22개 중 9개) |
| 빈 final(`--lp-min -0.5`, `t29_noise.wav`) | 엔진 로그 `[filtered lp …]`, 서버 로그 `버림: #N 빈 final`, DB에 행 없음, `segment_id` 빈틈없음. 흐린 줄이 화면에 남는 시간 기록 |
| 숫자와 문장부호 | 화면, txt, md에서 엔진이 낸 그대로 보임 |
| `demo_long.wav` | 기록: 문장 수, CER, final 지연 평균·최대. T28(16구간, 3.66%, 평균 0.84초·최대 1.23초)과 나란히 적음 |
| 엔진 준비 시간 | 기록: 엔진을 띄운 때부터 `ready`까지 |
