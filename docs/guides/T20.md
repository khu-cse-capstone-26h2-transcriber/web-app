# [T20] 실제 STT 연동: 기기 수신 경로(PR #1) 병합과 T29에서 찾은 문제 고치기 — 지침서

2026-11-10 · 이광호

## 목표

박지윤이 올린 web-app PR #1(`7b0c408`, 기기 결과 수신 경로)을 그대로 병합합니다. 그래서 기기(`audiostackd`)가 보낸 실제 엔진 결과가 웹 자막, DB, 히스토리, 내보내기까지 이어지게 합니다. 이것이 mock을 실제 STT로 바꾸는 일입니다.

같은 브랜치에서 T29 시험으로 찾아 2026-11-09에 고치기로 한 세 가지를 고칩니다.

1. 웹 버튼으로 시작한 녹음 중에 기기 세션이 시작되면, 웹이 앞 세션의 히스토리로 가 버려 새 기기 세션을 보여 주지 않습니다.
2. 기기의 `/end`가 DB 장애로 실패한 뒤 다시 보내면, 세션이 녹음 중으로 남습니다(리뷰 지적 `ingest.ts:101`).
3. 중단된 세션이 이유와 상관없이 `중단됨 (서버가 꺼져 끊김)`으로 보입니다.

노트북에서 실제 엔진(ONNX)과 `feed_wav.py`로 다시 시험해 확인한 뒤 `main`에 병합합니다.

## 배경과 전제, 범위

- **T29 결과(2026-11-09)**: PR #1의 수신 경로는 실제 엔진 결과로도 기대대로 동작했습니다. 정상 흐름, 빈 final 버림, 재전송, 세션 교체와 늦은 final 30초, 끊김과 재연결 모두 서버 로그·DB·화면이 맞았습니다. 고칠 점은 위 세 가지였습니다. 자세한 내용은 [`T29.md`](T29.md) '결과'에 있습니다.
- **'mock 교체'의 뜻**: 인식은 기기에서 하고, 서버는 결과를 HTTP로 받아 `DeviceSttAdapter`(PR #1)로 세션에 넣습니다. 기기가 세션을 시작하면 이 어댑터를 쓰고, 웹 '녹음 시작'은 지금처럼 `STT_MODE`(mock이 기본, local은 T28 실험)를 씁니다. 웹 버튼으로 기기 녹음을 시작·종료하는 일은 T27(`ctrl.sock`)에서 합니다.
- **T19와의 관계(2026-11-10 사용자 결정)**: 김범수(하드웨어)의 T19 합의를 기다리지 않고 노트북에서 끝냅니다. 수신 경로 이름(`/api/device/sessions`)과 `audiostack.conf` 변경은 아직 김범수가 동의하지 않았습니다. 바뀌면 그때 `device/routes.ts`와 `docs/device-ingest.md`를 고칩니다. 실제 데몬의 재전송, 세션 교체, 늦은 결과는 T26, T27에서 봅니다.
- **PR #1(`3185b0f`, `7b0c408`)이 바꾸는 파일** 11개
  - 서버: `migrations/003_device_session.sql`(`sessions.device_session_id`), `device/convert.ts`·`convert.test.ts`(결과를 `SttEvent`로, 테스트 5개), `device/ingest.ts`·`routes.ts`(수신 경로), `stt/device.ts`(`DeviceSttAdapter`), `sessions/manager.ts`(`start`에 어댑터와 기기 번호, `interruptActive`), `sessions/repository.ts`, `app.ts`
  - 웹: `RecordPage.tsx`(녹음하지 않는 동안 2초마다 진행 중인 녹음 확인)
  - 문서: `docs/device-ingest.md`
  - 의존성 변경은 없습니다. PR의 기준 커밋 `0d78cc1` 뒤로 `main`에는 문서 커밋만 있어 충돌이 없습니다(GitHub `MERGEABLE`).
- **고칠 점의 원인(코드를 읽어 확인)**
  1. 새 기기 세션: 서버는 기기 세션이 시작되면 웹 버튼 세션을 `interruptActive`로 닫습니다. 이 경로는 `ended`를 보내지 않고 스트림만 닫습니다. 웹(`useSessionStream`)은 이를 끊긴 것으로 보고 1초 뒤 진행 중인 세션을 묻습니다. 다른 세션(#6)이 돌아오면 `finish()`를 불러 `/history/5`로 가고, 그때 받은 #6은 버립니다.
  2. `/end`: `DeviceIngest.end()`는 `this.current`를 `sessions.stop()`보다 먼저 비웁니다. `stop()`이 DB 장애로 실패하면 데몬은 503을 받고 다시 보냅니다. 그러면 서버는 이 세션을 모르는 기기 세션으로 보고 200을 돌려줍니다. 결국 세션은 녹음 중으로 남습니다. 다음 세션 통지가 DB 장애 중에 오면 `interruptActive`가 저장하지 못한 final을 잃습니다(T29 curl 14~15).
  3. 표시: `SESSION_STATUS_LABELS.interrupted`가 `중단됨 (서버가 꺼져 끊김)`입니다. 이제는 기기 세션 시작으로도 중단되므로 이유가 틀릴 수 있습니다.
- **T17에서 넘어온 것**: 웹 `applyMessage`는 뒤 구간의 final이 와도 앞 구간의 partial을 지웁니다(`partial.segmentId <= message.segmentId`). 주석에는 "같은 segmentId의 final이 오면 비운다"고만 적혀 있습니다. 실제로는 서버가 `segmentId`를 붙이고, partial은 다음 final이 받을 번호를 씁니다. 그래서 앞 구간 partial이 남은 채 뒤 구간 final이 오는 일은 없습니다. 끊겼다가 final을 다시 받을 때는 `<=`가 지난 partial을 지워 줍니다. T29의 실제 엔진 시험에서도 문제가 없었습니다. 그래서 코드는 두고 주석만 맞춥니다.

범위는 다음과 같습니다.

  - 기기 세션 교체(`ended`) 때 새 세션 따라가기
  - 웹 버튼으로 기기 녹음 시작·종료(T27)
