# [T07] SSE 스트림 엔드포인트(mock 이벤트, heartbeat) — 지침서

2026-10-15 · 이광호

## 목표

녹음 중인 세션에 `GET /api/sessions/:id/events`로 접속하면 STT의 partial/final 이벤트가 생기는 즉시 SSE로 옵니다. 이벤트가 없어도 15초마다 heartbeat가 오고, 세션을 종료하면 `ended` 메시지가 온 뒤 스트림이 닫힙니다. T14(실시간 트랜스크립트 화면)는 이 스트림을 받아 그리고, T09(재연결 이어받기)는 여기에 빠진 이벤트를 채우는 기능을 더합니다.

## 배경과 전제, 범위

선행 작업은 T06(세션 API)이고 끝났습니다. 이벤트는 T06의 `SessionManager.handleEvent`에서 받아 갑니다. T08(세그먼트 저장)과는 상관없이 동작하고, 저장 동작은 바꾸지 않습니다. 확정된 결정 중 관련된 것은 'SSE로 시작하고 추후 WebSocket 전환을 고려해 설계', 'SSE 끊김은 자동 재연결과 화면 상단 배너'입니다. 실행 전에 Docker Desktop이 켜져 있고 `docker compose up -d`로 DB가 떠 있어야 합니다.

이 지침서는 T06, T08과 같이 구현과 같은 세션에서 썼습니다. 코드 전문은 싣지 않습니다. 코드는 저장소의 파일(커밋 `c5198fe`)이 기준이고, 여기에는 결정과 동작, 확인 방법을 적습니다.

- 하는 것: 공용 메시지 타입 `SessionStreamMessage`와 heartbeat 간격 상수, SSE 응답 하나를 맡는 `SseStream`, `SessionManager`의 구독(받는 쪽) 관리, 스트림 라우트, 서버를 끌 때 스트림을 닫는 처리.
- 하지 않는 것: SSE의 `id:` 줄과 `Last-Event-ID`로 빠진 이벤트 채우기(T09), 웹앱 화면(T14), 끊김 배너와 재연결 정책(T15), CORS(T12), 단위 테스트(T17).
- 협의가 필요해 가정하지 않는 것: 물리 버튼으로 녹음을 시작하는 경로(D4, 하드웨어 파트 김범수). 세션별 스트림이라 웹앱은 세션 번호를 알아야 접속할 수 있습니다. 버튼으로 시작한 녹음을 웹앱이 어떻게 알아챌지는 그 경로가 정해질 때 봅니다.

## 스트림 동작

메시지는 모두 SSE의 기본 `message` 이벤트로 보내고, `data` 한 줄에 JSON 하나입니다. 타입은 `packages/shared/src/stream.ts`의 `SessionStreamMessage`입니다.

| `type` | 언제 | 내용 |
| --- | --- | --- |
| `partial`, `final` | STT가 이벤트를 낼 때마다 | `SttEvent` 그대로 |
| `heartbeat` | 접속한 뒤 15초마다 | 없음 |
| `ended` | 세션 종료(`POST /api/sessions/:id/stop`)가 성공했을 때 | `session`: 닫힌 세션. 이 메시지 뒤에 서버가 스트림을 닫습니다 |

```text
data: {"type":"partial","segmentId":0,"text":"안녕하세요","startMs":0,"endMs":200}

data: {"type":"final","segmentId":0,"text":"안녕하세요 오늘 회의를 시작하겠습니다","startMs":0,"endMs":800}

data: {"type":"heartbeat"}

data: {"type":"ended","session":{"id":17,"status":"ended","startedAt":"2026-10-15T02:13:00.575Z","endedAt":"2026-10-15T02:13:06.625Z"}}
```

| 상황 | 일어나는 일 |
| --- | --- |
| 녹음 중인 세션에 접속 | `200`, `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`. 서버 로그에 `[stream] #N 연결 (지금 K개)` |
| 없는 번호, 끝난 세션, 잘못된 번호 | 세션 API와 같은 에러 JSON. 각각 `404` `SESSION_NOT_FOUND`, `409` `SESSION_NOT_ACTIVE`, `400` `INVALID_SESSION_ID`. 종료를 처리하는 중(`stopping`)에 접속해도 `409` |
| 여러 곳에서 동시에 접속 | 모두 같은 이벤트를 받습니다. 개수 제한은 없습니다 |
| 브라우저가 연결을 끊음 | 그 연결에만 그만 보냅니다. 로그에 `[stream] #N 연결 끊김 (지금 K개)`. 녹음과 저장은 그대로입니다 |
| 종료 성공 | `ended`를 보내고 스트림을 닫습니다 |
| 종료 실패(DB가 꺼짐 등, `500`) | 스트림은 그대로 열려 있고 heartbeat만 옵니다. 다시 종료해 성공하면 `ended`가 옵니다 |
| 서버 종료(Ctrl+C, `SIGTERM`) | `ended` 없이 스트림을 닫습니다. 세션은 T06대로 `interrupted`로 닫힙니다 |
| 스트림이 닫힌 뒤 브라우저 `EventSource`가 다시 접속 | 끝난 세션이라 `409`를 받고 다시 접속하지 않습니다(`readyState` 2) |

## 구현 순서

1. DB를 띄우고 `main`에서 새 브랜치를 만듭니다.

    ```bash
    docker compose up -d
    git switch -c feat/t07-sse-stream
    ```

2. `packages/shared/src/stream.ts`에 메시지 타입과 heartbeat 간격을 두고 `index.ts`에서 내보냅니다. 웹앱도 같은 타입과 간격을 씁니다.

    ```ts
    export const STREAM_HEARTBEAT_MS = 15_000;

    export type SessionStreamMessage =
      | SttEvent
      | { type: 'ended'; session: Session }
      | { type: 'heartbeat' };
    ```

3. `apps/server/src/http/sse.ts`에 `SseStream`을 씁니다. 세션이나 STT를 모르는, SSE 응답 하나만 맡는 클래스입니다.

    | 멤버 | 하는 일 |
    | --- | --- |
    | `constructor(res, { intervalMs, message })` | 응답과 heartbeat 설정을 받습니다. 아직 아무것도 보내지 않습니다. 응답의 `close`에 `close()`를 겁니다 |
    | `start()` | 헤더를 보내고(`flushHeaders`) heartbeat 타이머를 켭니다. 여러 번 불러도 한 번만 합니다 |
    | `send(data)` | `data: <JSON>\n\n`을 씁니다. 열리기 전이면 먼저 엽니다. 닫힌 뒤에는 아무것도 하지 않습니다 |
    | `close()` | 타이머를 끄고 응답을 끝냅니다. 여러 번 불러도 됩니다 |

    헤더를 `start()`까지 미루는 것은, 진행 중인 세션이 아닐 때 다른 API와 같은 에러 JSON으로 응답하기 위해서입니다. 닫힌 뒤에 쓰지 않는 것은, 끝난 응답에 쓰면 Node가 `error` 이벤트를 내고 듣는 곳이 없으면 서버가 죽기 때문입니다.

4. `apps/server/src/sessions/manager.ts`를 고칩니다.
    - `SessionSubscriber` 인터페이스(`send(message)`, `close()`)를 둡니다. 전송 방식을 모르는 모양이라 WebSocket으로 바꿔도 그대로 씁니다. `SseStream`이 이 모양을 따릅니다.
    - `ActiveSession`에 `subscribers: Set<SessionSubscriber>`를 둡니다.
    - `subscribe(id, subscriber)`: 진행 중인 그 세션이면 등록하고, 그만 받는 함수를 돌려줍니다. 아니면 `404`나 `409`를 던집니다. 이 구분은 `stop`에 있던 코드를 `notActiveError(id)`로 빼서 함께 씁니다.
    - `handleEvent`에서 개수를 센 뒤 partial과 final 모두 `broadcast`합니다. 받는 쪽 하나에서 예외가 나도 로그만 남기고 나머지와 STT 처리는 계속합니다. 이 함수는 어댑터의 타이머 안에서 불리므로, 예외가 새면 서버가 죽습니다.
    - `stop`에서 세션을 닫은 뒤 `{ type: 'ended', session }`을 보내고 받는 쪽을 모두 닫습니다. 종료가 실패하면 스트림은 건드리지 않습니다.
    - `disconnectSubscribers()`: 세션은 두고 받는 쪽만 닫습니다. 서버를 끌 때 씁니다.
    - `shutdown`에서도 남은 받는 쪽을 닫습니다.

5. `apps/server/src/sessions/routes.ts`에 `GET /:id/events`를 더합니다. 순서가 중요합니다.

    ```ts
    const stream = new SseStream(res, { intervalMs: STREAM_HEARTBEAT_MS, message: HEARTBEAT });
    const unsubscribe = await sessions.subscribe(id, stream); // 여기서 던지면 에러 JSON
    res.on('close', unsubscribe);
    stream.start();
    ```

6. `apps/server/src/index.ts`의 `shutdown`에서 `server.close(...)` 바로 뒤에 `sessions.disconnectSubscribers()`를 부릅니다. `server.close`는 열린 요청이 모두 끝나야 콜백을 부르는데, SSE 응답은 스스로 끝나지 않습니다. 이 줄이 없으면 브라우저가 연결을 끊을 때까지 서버가 꺼지지 않습니다(결과의 '확인한 값' 참고).

7. 동작을 확인하고 커밋합니다. push와 `main` 병합은 사용자가 따로 지시할 때 합니다.

    ```bash
    npm run typecheck
    npm run dev:server
    curl -X POST localhost:3000/api/sessions
    curl -N -i localhost:3000/api/sessions/N/events
    curl -X POST localhost:3000/api/sessions/N/stop
    git add packages/shared/src apps/server/src
    git commit -m "feat: 세션 SSE 스트림과 heartbeat 추가"
    ```

8. 기록을 남깁니다. `docs/logs/`의 그날 일지, `docs/project-overview.md`, 이 지침서의 '결과'를 채웁니다. `TODO.md`는 변경안을 사용자에게 먼저 보고한 뒤 허락을 받고 고칩니다.

## 결정 사항과 남은 질문

- 이미 정한 것: 위 '착수 전 확인'의 다섯 가지, SSE로 시작해 WebSocket 전환을 고려한다는 것, 단일 사용자라 진행 중인 세션은 하나라는 것(T06), 세션 API의 에러 형식(T04, T06).
- 이 지침서에서 정한 것:
  - **heartbeat도 `data` 안의 메시지(`{"type":"heartbeat"}`)로 보냅니다.** SSE의 주석 줄(`: ping`)은 브라우저 코드에서 보이지 않아, 연결이 소리 없이 죽었을 때 웹앱이 알아챌 수 없습니다. 메시지로 보내면 T15에서 '30초 넘게 아무 메시지도 없으면 끊긴 것으로 본다' 같은 처리를 할 수 있고, WebSocket으로 바꿔도 같습니다. 대신 웹앱은 이 메시지를 무시하는 처리가 필요합니다.
  - **종료가 성공하면 `ended`를 보내고 서버가 스트림을 닫습니다.** `EventSource`는 연결이 끊기면 스스로 다시 접속하므로, 웹앱이 끝을 알 수 있게 했습니다.
  - **진행 중이 아닌 세션에 접속하면 다른 API와 같은 에러 JSON으로 응답합니다.** `EventSource`는 200이 아닌 응답을 받으면 다시 접속하지 않습니다. 브라우저 코드에서 상태 코드는 보이지 않으므로, 웹앱이 이유를 알려면 `GET /api/sessions/active`를 봅니다.
  - **종료를 처리하는 중(`stopping`)에는 접속을 받지 않습니다(`409`).**
  - **동시 접속 수에 제한을 두지 않았습니다.**
  - **종료가 실패하면 스트림을 닫지 않습니다.** 세션이 녹음 중으로 남으므로 스트림도 남깁니다.
  - **서버를 끌 때는 `ended` 없이 스트림을 닫습니다.** 세션을 `interrupted`로 닫는 일은 처리 중인 요청이 끝난 뒤(T06 순서 그대로)에 하므로, 그 전에 스트림을 닫아야 서버가 꺼집니다. 브라우저는 서버가 다시 뜰 때까지 접속을 시도하다가, 다시 뜬 뒤에는 `409`를 받고 멈춥니다.
  - **접속 전 이벤트는 쌓아 두지 않습니다.** 세션을 시작하고 접속하기까지의 사이에 온 partial 한두 개는 받지 못할 수 있습니다. partial은 누적 텍스트라 다음 것이 덮어써서 화면에는 차이가 없습니다. 실제 확인에서는 첫 partial(0.2초)부터 받았습니다.
  - **`SessionSubscriber`는 전송 방식을 모릅니다.** SSE 코드는 `http/sse.ts`와 라우트에만 있습니다. WebSocket으로 바꿀 때는 같은 모양의 받는 쪽을 하나 더 만들면 됩니다.
  - **`[stream]` 로그를 더했습니다.** 접속과 끊김 때 지금 연결 수를 찍습니다. 세션이 끝나며 서버가 닫은 연결은 찍지 않습니다.
- 아직 정해야 하는 것:
  - 이벤트 `id:`를 어떻게 붙이고, 재접속 때 무엇을 다시 보낼지 (T09). final은 DB(T08)에 있으므로, 예를 들어 final에만 `segmentId`를 `id`로 붙이고 재접속 때 그 뒤의 final을 DB와 저장 대기열에서 다시 보내는 방법이 있습니다.
  - 새로고침한 화면에 그 전 문장을 채울지 (T09 또는 T14). 지금은 접속한 뒤의 것만 옵니다.
  - 웹앱을 다른 포트(개발 서버)에서 띄울 때의 CORS (T12).
  - 물리 버튼으로 시작한 녹음을 웹앱이 알아채는 방법 (D4, 하드웨어 파트 김범수).
  - 동시 접속 수 상한. Rubik Pi의 메모리를 재는 T21 때 봅니다.
  - T06, T08에서 넘어온 것은 그대로입니다: 세션 API의 500을 503으로 맞출지(T13 전), 강제로 꺼진 세션의 `ended_at` 보정, 정지할 때 말하던 문장(D4의 C3), 저장 대기열 상한(T21).
