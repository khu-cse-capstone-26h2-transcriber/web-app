# [T13] 녹음 제어 UI — 지침서

2026-10-20 · 이광호

## 목표

웹앱의 녹음 화면(`/`)이 진행 중인 녹음의 상태를 보여 주고, 웹에서도 녹음을 시작하고 끝낼 수 있게 합니다. 녹음 중에는 `녹음 중 · 01:23 (#12)`처럼 흐른 시간과 세션 번호가 보이고, 웹에서 끝내면 히스토리 상세로 넘어갑니다. 녹음의 주 제어는 기기의 물리 버튼이고, 이 화면의 버튼은 개발·시연·원격 종료용 보조 수단입니다. 서버는 DB에 닿지 못했을 때 `500` 대신 `503` `DB_UNAVAILABLE`로 답해, 화면이 "잠시 뒤 다시"라고 안내할 수 있게 합니다.

## 배경과 전제, 범위

선행 작업 T06(세션 API)과 T12(웹앱 뼈대)는 끝났습니다. 실행 전에 Docker Desktop이 켜져 있고 `docker compose up -d`로 DB가 떠 있어야 하며, 루트 `.env`가 있어야 합니다.

이 지침서는 T06~T12와 같이 구현과 같은 세션에서 썼습니다. 코드 전문은 싣지 않습니다. 코드는 저장소의 파일(커밋 `a6589cf`)이 기준이고, 여기에는 결정과 동작, 확인 방법을 적습니다.

- 하는 것: 녹음 화면의 상태 표시(확인 중, 녹음하고 있지 않음, 녹음 중과 흐른 시간), '녹음 시작'·'녹음 종료' 버튼, 409·503·서버 꺼짐일 때의 문구, 웹 API 함수 3개, 서버 공통 에러 처리의 `503`.
- 하지 않는 것: 실시간 자막과 SSE 클라이언트(T14), 끊김 배너와 서버 상태 다시 확인(T15), 화면을 열어 둔 동안 다른 곳에서 시작·종료한 녹음을 바로 알아채는 것(D4 뒤), 물리 버튼 신호를 받는 서버 경로(D4, T19·T20), 디자인.

## 화면과 서버 변경

녹음 화면의 상태는 여섯 가지입니다.

| 상태 | 화면 |
| --- | --- |
| 확인 중 | `녹음 상태를 확인하는 중…` |
| 확인 실패 | `녹음 상태를 확인하지 못했습니다: {서버의 message}`와 '다시 확인' 버튼 |
| 녹음하지 않음 | `녹음하고 있지 않습니다`와 '녹음 시작' |
| 시작 중 | `시작하는 중…`, '녹음 시작'은 눌리지 않음 |
| 녹음 중 | `녹음 중 · 00:03 (#35)`와 '녹음 종료' |
| 종료 중 | `종료하는 중… · 00:11 (#35)`, '녹음 종료'는 눌리지 않음 |

시작·종료가 실패했을 때는 버튼 아래에 문구를 보여 주고, 다음에 버튼을 누르면 지웁니다.

| 상황 | 화면 |
| --- | --- |
| 시작했는데 이미 녹음 중 (`409` `SESSION_ALREADY_ACTIVE`) | 진행 중인 녹음을 다시 확인해 보여 주고 `이미 진행 중인 녹음이 있어 그 녹음을 보여 줍니다` |
| 종료했는데 이미 끝남 (`409` `SESSION_NOT_ACTIVE`, `404`) | 다시 확인하고 `이미 끝난 녹음입니다 (#36)` |
| 시작할 때 DB가 꺼짐 (`503`) | `녹음을 시작하지 못했습니다: DB에 연결하지 못했습니다` |
| 종료할 때 DB가 꺼짐 (`503`) | `녹음을 종료하지 못했습니다: DB에 연결하지 못했습니다. 잠시 뒤 다시 종료해 주세요`. 녹음 중으로 남아 다시 누를 수 있음 |
| 서버가 꺼짐 | `서버에 연결하지 못했습니다`가 들어간 같은 문구 |

화면 아래에는 '녹음은 기기의 버튼으로 시작·종료하고, 이 버튼은 보조용이며, 기기 버튼으로 시작한 녹음이 보이지 않으면 새로고침하라'는 안내를 둡니다.

| 파일 | 바뀐 것 |
| --- | --- |
| `apps/web/src/api/endpoints.ts` | `getActiveSession(signal)`, `startSession()`, `stopSession(id)`. 응답의 `{ session }`을 벗겨 `Session`(또는 `null`)을 돌려줍니다 |
| `apps/web/src/api/client.ts` | `toApiError(error)`: 잡은 에러를 `ApiError`로 맞춥니다. `useApiData`에 있던 변환을 옮겨 녹음 화면과 같이 씁니다 |
| `apps/web/src/pages/RecordPage.tsx` | 위 상태와 버튼, 흐른 시간(`ElapsedTime`, 1초마다) |
| `apps/server/src/db/errors.ts` | `isDbUnavailable(error)`: DB에 닿지 못해 생긴 에러인지 가립니다 |
| `apps/server/src/http/errors.ts` | `errorHandler`가 `isDbUnavailable`이면 로그 한 줄을 남기고 `503` `DB_UNAVAILABLE`로 답합니다 |

`isDbUnavailable`이 DB 연결 실패로 보는 것은 세 가지입니다.

- Node의 소켓 에러 코드: `ECONNREFUSED`, `ECONNRESET`, `ETIMEDOUT`, `EHOSTUNREACH`, `ENETUNREACH`, `ENOTFOUND`, `EAI_AGAIN`, `EPIPE`
- PostgreSQL SQLSTATE: `08`로 시작하는 연결 예외, `57P01`~`57P03`(DB가 꺼지는 중이거나 켜지는 중)
- pg가 코드 없이 메시지로만 알리는 것: `timeout exceeded when trying to connect`, `Connection terminated`(연결 대기 시간 2초 초과, 연결 중 끊김)

## 구현 순서

1. Docker Desktop을 켜고 DB를 띄운 뒤 `main`에서 새 브랜치를 만듭니다.

    ```bash
    docker compose up -d --wait
    git switch -c feat/t13-record-control
    ```

2. 서버: `db/errors.ts`에 `isDbUnavailable`을 두고, `http/errors.ts`의 `errorHandler`에서 `HttpError`와 JSON 파싱 에러 다음, 예상하지 못한 에러 앞에서 확인합니다. `/health`는 자체 `try/catch`가 있어 그대로 둡니다.

3. 서버를 띄우고 curl로 `503`을 확인합니다(아래 완료 기준). DB를 끌 때는 `docker compose stop db`, 연결 대기 시간 초과를 볼 때는 `docker compose pause db`를 씁니다. `pause`로 시험할 때는 풀에 쉬고 있는 연결이 닫히도록 마지막 DB 요청 뒤 10초 넘게 기다린 다음 멈춥니다.

4. 웹: `client.ts`에 `toApiError`를 두고 `useApiData`가 쓰게 바꿉니다. `endpoints.ts`에 세션 API 함수 3개를 더하고, `RecordPage.tsx`를 채웁니다.

5. 동작을 확인하고 커밋합니다. push와 `main` 병합은 사용자가 따로 지시할 때 합니다.

    ```bash
    npm run typecheck
    npm run build -w @app/web
    npm run dev:server   # 다른 터미널
    npm run dev:web      # http://localhost:5173
    git add apps/server/src/db/errors.ts apps/server/src/http/errors.ts apps/web/src
    git commit -m "feat: 녹음 제어 화면과 DB 연결 실패 503 응답 추가"
    ```

6. 기록을 남깁니다. `docs/logs/`의 그날 일지, `docs/project-overview.md`, 이 지침서의 '결과'를 채웁니다. `TODO.md`는 변경안을 사용자에게 먼저 보고한 뒤 허락을 받고 고칩니다.

## 완료 기준

브라우저 확인은 Claude 데스크톱 앱의 브라우저 패널에서 했습니다. 'psql과 같음'은 `docker compose exec db psql -U user -d transcriber`로 같은 내용을 읽어 비교한다는 뜻입니다. 밖에서 시작·종료하는 것은 curl로 물리 버튼을 대신한 것입니다.

| 명령어 | 기대 출력 |
| --- | --- |
| `npm run typecheck` | tsc 에러 없이 종료 코드 0 |
| `npm run build -w @app/web` | `✓ built` |
| `docker compose stop db` 뒤 curl `/health`, `POST /api/sessions`, `GET /api/sessions`, `GET /api/sessions/1` | 모두 `503` `{"error":{"code":"DB_UNAVAILABLE","message":"DB에 연결하지 못했습니다"}}` |
| 같은 상태에서 `GET /api/sessions/active` | `200` `{"session":null}` (메모리만 읽음) |
| 녹음 중에 DB를 끄고 `POST /api/sessions/:id/stop` | `503`. `active`에 그 세션이 녹음 중으로 남음. DB를 켜고 다시 종료하면 `200`, psql에서 `ended`와 세그먼트 행 |
| `docker compose pause db` 뒤 `POST /api/sessions` | 약 2초 뒤 `503`. 서버 로그 `[server] DB에 연결하지 못했습니다: Connection terminated due to connection timeout` |
| 브라우저 `/` | `녹음하고 있지 않습니다`, '녹음 시작' |
| '녹음 시작' | `녹음 중 · 00:00 (#N)`. 몇 초 뒤 흐른 시간이 늘어남 |
| 녹음 중 새로고침 | 같은 세션이 녹음 중으로 보임 |
| '녹음 종료' | `/history/N`으로 이동, 상태 `ended`, 세그먼트 개수가 psql과 같음 |
| 화면이 '녹음하고 있지 않습니다'일 때 curl로 시작한 뒤 '녹음 시작' | `이미 진행 중인 녹음이 있어 그 녹음을 보여 줍니다`와 curl로 시작한 세션 |
| 그 녹음을 curl로 끝낸 뒤 '녹음 종료' | `이미 끝난 녹음입니다 (#N)`, `녹음하고 있지 않습니다` |
| curl로 시작한 뒤 `/` 열기 | 그 세션이 녹음 중으로 보임 |
| 녹음 중에 DB를 끄고 '녹음 종료' | `녹음을 종료하지 못했습니다: DB에 연결하지 못했습니다. 잠시 뒤 다시 종료해 주세요`, '녹음 종료'를 다시 누를 수 있음. DB를 켜고 누르면 `/history/N`, 세그먼트 개수가 psql과 같음 |
| DB를 끄고 '녹음 시작' | `녹음을 시작하지 못했습니다: DB에 연결하지 못했습니다`, `녹음하고 있지 않습니다` |
| 서버를 끄고 `/` | `녹음 상태를 확인하지 못했습니다: 서버에 연결하지 못했습니다`, '다시 확인'. 서버를 켜고 누르면 `녹음하고 있지 않습니다` |
| DB를 멈추고(`pause`) '녹음 시작'을 누른 직후 | `시작하는 중…`, 버튼 `disabled`. 약 2초 뒤 시작 실패 문구와 함께 다시 누를 수 있음 |
| 브라우저 콘솔 | 위에서 일부러 만든 `409`, `502`, `503` 응답 기록만 있고 스크립트 에러 없음 |
| 서버에 `SIGINT` | `[server] 종료 완료` |
| `npm run db:migrate` | `skip` 두 줄, `새로 적용 0개, 전체 2개` |
| `npm run dev:stt` | `[stt]` 15줄 |
| `git branch --show-current` | `feat/t13-record-control` |
| `git log --oneline -1` (코드 커밋 직후) | `feat: 녹음 제어 화면과 DB 연결 실패 503 응답 추가` |

## 결정 사항과 남은 질문

- 이미 정한 것: 위 '착수 전 확인'의 일곱 가지, 세션 API의 응답과 상태 전이(T06), 종료가 실패하면 세션을 녹음 중으로 남기는 동작(T06, T08), API 클라이언트와 에러 형식(T12).
- 이 지침서에서 정한 것:
  - **DB 연결 실패는 에러 코드와 메시지로 가립니다.** pg는 연결 대기 시간 초과와 연결 중 끊김에 코드를 붙이지 않아 메시지(`timeout exceeded when trying to connect`, `Connection terminated`)로 봅니다. pg 판이 바뀌어 문구가 달라지면 `500`으로 돌아가므로, pg를 올릴 때 다시 확인합니다.
  - **503 로그는 한 줄입니다.** `[server] DB에 연결하지 못했습니다: {이유}`. 예상하지 못한 에러처럼 스택을 찍지 않습니다.
  - **`/health`는 바꾸지 않았습니다.** 이미 모든 에러를 `503`으로 답하고 있습니다.
  - **`toApiError`를 `client.ts`로 옮겼습니다.** T12의 `useApiData`에 있던 변환과 같은 일을 녹음 화면도 하므로 한 곳에 둡니다.
  - **에러 코드는 웹에서 문자열로 비교합니다**(`SESSION_ALREADY_ACTIVE`, `SESSION_NOT_ACTIVE`, `SESSION_NOT_FOUND`). 서버도 코드를 문자열로 바로 쓰고 있어 공용 타입은 만들지 않았습니다. 서버가 코드를 상수로 쓰게 되면 `packages/shared`로 함께 옮깁니다.
  - **흐른 시간은 서버의 `startedAt`과 브라우저 시계로 계산합니다.** 1초마다 다시 그리고, 음수는 `00:00`으로 보이며, 한 시간이 넘으면 `h:mm:ss`입니다.
  - **409를 받은 뒤의 다시 확인도 '확인 중'을 거칩니다.** 잠깐 버튼이 사라졌다가 결과에 맞는 버튼이 나옵니다.
  - **종료가 실패한 뒤에도 '녹음 중'으로 보입니다.** 서버가 세션을 녹음 중으로 남기기 때문입니다. 다만 서버는 종료할 때 STT를 먼저 끄므로(T06), 이때는 새 문장이 더 오지 않습니다.
- 아직 정해야 하는 것:
  - 화면을 열어 둔 동안 다른 곳에서 시작·종료한 녹음을 알아채는 방법(폴링 또는 알림 스트림). D4에서 물리 버튼 신호가 서버에 오는 방식이 정해진 뒤에 고릅니다. [하드웨어]
